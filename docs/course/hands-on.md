# 핸즈온 실습 진행서

> 이 문서는 실습 자료의 원본입니다. 단계별 HTML 자료는 여기서 확정한 내용으로 만듭니다.
> 결정하지 않은 단계는 비워 두고, 확정할 때마다 채웁니다. HTML을 먼저 만들지 않습니다.

강의 덱([index.html](index.html))이 끝난 뒤부터가 이 문서의 범위입니다. 수강생이 손으로 하는 전부를 여덟 단계로 나눕니다.

## 용어

같은 것을 여러 이름으로 부르면 실습장에서 바로 막힙니다. 아래 표의 왼쪽 말만 씁니다.

| 쓰는 말 | 뜻 | 쓰지 않는 말 |
|---|---|---|
| 실습 단계 | 이 문서의 1단계부터 8단계까지. 수강생이 손으로 하는 순서 | 단위, 파트 |
| 강의 세션 | [curriculum.md](../curriculum.md)의 여덟 세션. 시간이 배정된 진행 구획 | 단위. 한국어로 강의를 세는 말이 아닙니다 |
| 실습 위키 | 수강생이 만들어 끝까지 쓰는 위키. `~/engram-wiki` | 랩, lab, 내 위키 |
| 데모 위키 | 저장소의 `examples/personal`. 6단계에서만 씁니다 | 씨앗 위키, seed, 예제 위키 |
| 실습 재료 | 저장소의 `examples/materials/`. 위키에 집어넣을 원재료 | 샘플, 교재, 데이터셋 |
| 저장소 | 1단계에서 클론한 engram 소스 저장소. `~/engram`. **실습 위키가 아닙니다** | 레포, 리포지토리 |
| 설치 방법 | 소스 빌드와 바이너리 내려받기 두 가지 | 갈래, 경로, 트랙 |

`갈래`는 커맨드 분류(넣기, 올리기, 조회, 재발견, 관리 다섯 갈래)에만 씁니다. 설치나 선택지를 가리키는 데 쓰지 않습니다.

**강의는 세션으로 세고 실습은 단계로 셉니다.** 세션은 시간이 배정된 진행 구획이라 강사가 쓰는 말이고, 단계는 순서가 있는 작업이라 수강생이 쓰는 말입니다. 자료 안의 장 구분을 가리킬 때만 챕터를 씁니다.

실습 단계와 강의 세션은 번호가 어긋납니다. 강의 1세션은 덱이라 손을 쓰지 않고, 실습 1단계는 설치입니다. 대응은 아래와 같습니다.

| 실습 단계 | 강의 세션 |
|---|---|
| (없음) | 1세션 오리엔테이션 |
| 1단계 설치와 준비, 2단계 첫 위키 | 2세션 설치와 첫 위키 |
| 3단계 | 3세션 넣기 |
| 4단계 | 4세션 올리기 |
| 5단계 | 5세션 꺼내 쓰기 |
| 6단계 | 6세션 다시 만나기 |
| 7단계 | 7세션 에이전트 심화 |
| 8단계 | 8세션 운영과 공유 |

## 진행 상태

| 실습 단계 | 주제 | 상태 |
|---|---|---|
| 1 | 설치와 준비 | 확정 |
| 2 | 첫 위키 | 확정 |
| 3 | 넣기 | 확정 |
| 4 | 올리기 (에이전트 연결 포함) | 확정 |
| 5 | 꺼내 쓰기 | 미확정 |
| 6 | 다시 만나기 | 미확정 |
| 7 | 에이전트 심화 (MCP, 자동 분류) | 미확정 |
| 8 | 운영과 공유 | 미확정 |

## 전체를 관통하는 결정

단계마다 되풀이하지 않도록 여기 모읍니다.

**위키는 하나입니다.** 수강생은 1단계에서 `engram init`으로 `~/engram-wiki`를 만들고 8단계까지 그것만 씁니다. 실습 재료를 거기에 집어넣고, 승급하고, 검색하고, 반출합니다. 실습장을 여럿 만들지 않습니다.

**데모 위키는 6단계에서만 씁니다.** `resurface`와 `bridge`는 문서가 쌓이고 시간이 지나야 결과가 나옵니다. 수강생이 하루에 쓴 문서 예닐곱 개로는 아무것도 나오지 않습니다. 3단계부터 5단계까지는 빈 위키에서 시작하는 것이 오히려 맞습니다. 채우는 과정 자체가 그 단계의 내용이기 때문입니다.

**실습 재료는 저장소에서만 받습니다.** 바이너리에 넣지 않습니다. 위키 도구가 위키가 아닌 파일을 뿌리는 것은 역할에 맞지 않고, 바이너리만 커집니다. 그래서 바이너리를 내려받아 설치한 수강생도 저장소를 따로 받아야 합니다.

**실습 재료는 합성 자료입니다.** 조직 식별자가 들어가지 않습니다. 저장소가 공개 예정이기 때문입니다.

**문체는 경어체입니다.** 수강생에게 직접 말하는 자료입니다. 다만 문장을 늘리지 않습니다.

# 1단계. 설치와 준비

## 목표

engram이 어디서든 실행되는 상태를 만들고, 실습 재료를 손에 넣습니다.

## 설치 방법 둘

수강생이 처한 상황이 다르므로 두 가지로 나눕니다. 어느 쪽이든 저장소가 필요합니다. 실습 재료가 거기 있기 때문입니다.

| 방법 | 고르는 사람 | 얻는 것 |
|---|---|---|
| A. 소스 빌드 | Go를 이미 쓰거나 설치할 수 있는 사람 | 바이너리, 실습 재료, 데모 위키를 한 번에 |
| B. 바이너리 내려받기 | Go를 깔고 싶지 않은 사람 | 바이너리만. 실습 재료는 저장소를 따로 받습니다 |

강사는 A를 기본으로 안내하고, Go 설치에서 막히는 수강생에게 B로 넘어가게 합니다.

## 방법 A. 소스 빌드

전제는 둘입니다. **Go 1.26 이상**과 **git**입니다.

**홈 디렉토리에 클론합니다.** 3단계부터 실습 재료를 저장소 경로로 참조합니다. 다른 곳에 클론해도 되지만 그때는 3단계의 경로를 자기 위치로 바꿔야 합니다.

```
cd ~
git clone https://github.com/neocode24/engram.git
cd engram
go install ./cmd/engram
```

운영체제와 상관없이 이 세 줄이 전부입니다. **`sudo`를 쓰지 않습니다.** 관리자 권한을 요구하는 설치는 사내 기기에서 막히는 경우가 있고, 실습을 위해 시스템 디렉토리를 건드릴 이유가 없습니다.

`go install`은 `go env GOPATH`가 가리키는 곳의 `bin`에 넣습니다.

| 운영체제 | 들어가는 위치 |
|---|---|
| macOS, Linux | `~/go/bin/engram` |
| Windows | `%USERPROFILE%\go\bin\engram.exe` |

### PATH에 넣기

**이 디렉토리는 PATH에 자동으로 들어가지 않습니다.** Go 설치 프로그램은 Go 자신의 `bin`만 PATH에 넣습니다. 한 번 넣어 두면 이후 `go install`로 받는 모든 도구에 통합니다.

먼저 위치를 확인합니다.

```
go env GOPATH
```

macOS와 Linux의 zsh입니다. bash면 `~/.zshrc`를 `~/.bashrc`로 바꿉니다.

```
cat >> ~/.zshrc <<'EOF'

# go install 로 받은 도구. engram 이 여기 들어갑니다
export PATH="$PATH:$(go env GOPATH)/bin"
EOF
source ~/.zshrc
```

빈 줄과 주석을 함께 넣습니다. 나중에 설정 파일을 열었을 때 이 줄이 왜 있는지 알 수 있어야 합니다.

Windows PowerShell입니다. 사용자 범위로만 바꾸므로 관리자 권한이 필요 없습니다.

```powershell
$dir = Join-Path (go env GOPATH) "bin"
$cur = [Environment]::GetEnvironmentVariable("Path", "User")
[Environment]::SetEnvironmentVariable("Path", "$cur;$dir", "User")
```

**`setx PATH ...`를 쓰지 않습니다.** 1024자에서 잘리며 기존 PATH를 날릴 수 있습니다.

터미널을 닫았다 다시 엽니다. PATH 변경은 새 프로세스부터 적용됩니다.

## 방법 B. 바이너리 내려받기

### 내려받기

GitHub Releases에서 자기 플랫폼 아카이브를 받습니다. 이름 규칙은 `engram_<버전>_<운영체제>_<아키텍처>` 입니다.

| 운영체제 | 아키텍처 | 확장자 |
|---|---|---|
| darwin | amd64, arm64 | `.tar.gz` |
| linux | amd64, arm64 | `.tar.gz` |
| windows | amd64, arm64 | `.zip` |

Apple Silicon Mac은 `darwin_arm64`, Intel Mac은 `darwin_amd64`입니다. 헷갈리면 `uname -m`으로 확인합니다. `arm64`가 나오면 앞쪽입니다.

같은 릴리스의 `checksums.txt`로 검증합니다.

```
shasum -a 256 engram_1.0.0_darwin_arm64.tar.gz
```

출력이 `checksums.txt`의 해당 줄과 같아야 합니다.

### Homebrew (macOS, Linux)

tap이 켜지면 아래 한 줄이 됩니다. **지금은 꺼져 있습니다.** 저장소 공개 전환과 함께 켭니다.

```
brew install neocode24/tap/engram
```

Homebrew가 알아서 PATH 위에 놓으므로 따로 할 일이 없습니다. 위치는 Apple Silicon이 `/opt/homebrew/bin/engram`, Intel Mac과 Linux가 `/usr/local/bin/engram`입니다.

### 아카이브 직접 배치

Homebrew를 쓰지 않거나 Windows인 경우입니다. 압축을 풀면 `engram`(Windows는 `engram.exe`)이 나옵니다.

방법 A와 **같은 자리에 둡니다.** 설치 방법이 둘이어도 실행 파일이 있는 곳은 하나로 맞춥니다.

```
mkdir -p ~/go/bin
mv engram ~/go/bin/
```

Go가 깔려 있지 않아도 상관없습니다. 그냥 디렉토리 하나입니다. 그 뒤 방법 A의 PATH 설정을 그대로 따릅니다. Windows도 `%USERPROFILE%\go\bin`에 둡니다.

macOS에서 처음 실행하면 서명되지 않은 바이너리라 Gatekeeper가 막습니다. 시스템 설정의 개인정보 보호 및 보안에서 한 번 허용하거나 아래를 돌립니다.

```
xattr -d com.apple.quarantine ~/go/bin/engram
```

### 실습 재료 받기

바이너리만으로는 실습을 시작할 수 없습니다. 저장소를 받습니다. 빌드는 하지 않습니다. **방법 A와 같은 자리인 홈 디렉토리에 둡니다.**

```
cd ~
git clone https://github.com/neocode24/engram.git
```

## 확인

설치 방법과 운영체제에 상관없이 아래 셋이 통과해야 1단계가 끝납니다.

```
engram version
engram --help
engram doctor
```

- `version`이 버전과 빌드 정보를 냅니다. 방법 A로 빌드하면 버전이 `dev`로 나오는 것이 정상입니다.
- `--help`가 커맨드 스물여덟을 냅니다. **이 목록이 진실원입니다.** 문서와 다르면 문서가 틀린 것입니다.
- `doctor`가 환경을 진단합니다. 아직 위키가 없으므로 위키 관련 항목은 건너뜁니다.

`command not found`가 나면 PATH 문제입니다. 터미널을 새로 열었는지부터 확인합니다.

## 출력 언어

기본은 한국어입니다. 이 문서에 실린 출력도 한국어입니다. 영어로 보려면 둘 중 하나를 씁니다.

```
engram --lang en status
export ENGRAM_LANG=en
```

허용값은 `ko`와 `en`입니다. **실습 중에는 한국어로 둡니다.** 이 문서의 출력과 화면이 같아야 막혔을 때 비교할 수 있습니다.

이 설정은 `engram.yaml`에 없습니다. 그 파일은 커밋되어 팀이 공유하는데 출력 언어는 읽는 사람의 것이기 때문입니다([0049](../decisions/0049-cli-output-language.md)).

## 설치가 겹쳤을 때

**설치 방법은 하나만 고릅니다.** 그런데 실습 중에 방법을 바꾸거나, 이전에 Homebrew로 깔아 둔 것이 남아 있으면 두 개가 공존합니다. 이때 어느 쪽이 실행되는지는 **PATH에 먼저 나오는 디렉토리**가 정합니다. Homebrew는 자기 디렉토리를 PATH 앞에 붙이고 `~/go/bin`은 보통 뒤에 붙이므로 Homebrew 쪽이 이깁니다. 수강생이 소스를 고치고 `go install`을 다시 돌려도 바뀐 것이 실행되지 않는 상황이 여기서 나옵니다.

전부 찾습니다.

```
which -a engram          # macOS, Linux
where.exe engram         # Windows
```

지금 실행되는 것이 어느 쪽인지는 버전으로 구분합니다.

```
engram version
```

| 출력 | 어느 설치인가 |
|---|---|
| `dev` | 소스 빌드(`go install`). 릴리스 빌드만 버전을 새겨 넣습니다 |
| `1.0.0` 같은 번호 | Homebrew나 릴리스 아카이브 |

정리하려면 안 쓸 쪽을 지웁니다.

```
brew uninstall engram             # Homebrew 쪽을 버릴 때
rm "$(go env GOPATH)/bin/engram"  # 소스 빌드 쪽을 버릴 때
```

Windows는 `Remove-Item "$env:USERPROFILE\go\bin\engram.exe"` 입니다.

## Windows 수강생에게 추가로 안내할 것

- **Windows Terminal을 권합니다.** engram은 콘솔 코드 페이지를 UTF-8로 바꿔서 한글을 냅니다([ADR 0026](../decisions/0026-windows-console-utf8.md)). 구형 conhost에서도 깨지지 않지만 글꼴에 따라 표가 어긋나 보일 수 있습니다.
- 위키 경로를 인자로 줄 때 역슬래시를 씁니다. `engram lint C:\Users\...\engram-wiki` 형태입니다.
- 파일명에 한글을 쓰므로 경로에 공백이 있으면 따옴표로 감쌉니다.

## 강사 노트

- 1단계는 15분을 넘기지 않습니다. Go 설치에서 막히는 수강생이 나오면 그 자리에서 방법 B로 넘깁니다. 전원이 같은 방법일 필요가 없습니다.
- 실습 재료 위치를 각자 적어 두게 합니다. 3단계에서 계속 참조합니다.
- `engram --help` 출력을 다 같이 한 번 훑습니다. 커맨드가 넣기, 올리기, 조회, 재발견, 관리 다섯 갈래로 나뉜다는 것만 짚고 넘어갑니다. 개별 커맨드는 각 단계에서 다룹니다.

## 이 단계에서 확정한 것

| 결정 | 내용 | 이유 |
|---|---|---|
| 설치 방법 | 소스 빌드와 바이너리 내려받기 둘로 나눕니다 | Go 설치가 진입 장벽이 되면 안 됩니다 |
| 소스 빌드 | `go install` 하나만 안내합니다. `go build`와 수동 배치는 쓰지 않습니다 | 운영체제 셋에서 같은 한 줄이고 옮기는 단계가 없습니다 |
| sudo | 안내하지 않습니다. `/usr/local/bin`에 직접 넣지 않습니다 | 관리자 권한이 막힌 기기가 있고, 실습이 시스템 디렉토리를 건드릴 이유가 없습니다 |
| 실행 파일 위치 | 설치 방법과 무관하게 `~/go/bin`(Windows는 `%USERPROFILE%\go\bin`)으로 통일합니다 | 설치 방법이 둘이어도 자리는 하나여야 뒤섞이지 않습니다. Homebrew만 예외로 자기 자리를 씁니다 |
| 겹침 처리 | `which -a`로 찾고 `engram version`으로 구분합니다 | 소스 빌드는 `dev`, 릴리스는 번호가 나오므로 구분이 확실합니다 |
| 실습 재료 배포 | 저장소 클론으로만 얻습니다 | 바이너리에 임베드하면 위키 도구가 위키 아닌 파일을 뿌리게 됩니다 |
| Windows PATH | PowerShell의 `SetEnvironmentVariable`을 씁니다 | `setx`는 PATH를 자르거나 날립니다 |
| 클론 위치 | 홈 디렉토리 `~/engram` | 3단계가 저장소 경로로 재료를 읽습니다. 실습 위키 `~/engram-wiki` 와 이름이 비슷하므로 문서에서 늘 함께 적습니다 |
| 출력 언어 | 실습 중에는 한국어로 둡니다 | 문서에 실린 출력과 화면이 같아야 막혔을 때 비교됩니다 |

# 2단계. 첫 위키

## 목표

자기 위키를 만들고, 이 위키에 적용되는 규칙이 무엇인지 읽습니다. 아직 문서를 넣지 않습니다.

이 단계가 심는 문장은 하나입니다. **디렉토리는 분류함이 아니라 성숙 단계입니다.**

## 만들기

```
engram init --preset personal ~/engram-wiki
cd ~/engram-wiki
```

`--preset`은 생략해도 `personal`입니다. 그래도 적는 이유는 프리셋이라는 것이 있다는 사실을 여기서 알려야 하기 때문입니다.

### 속성이란

먼저 이 말을 짚습니다. 앞으로 계속 나옵니다.

**속성은 문서 맨 위 프론트매터에 들어가는 필드 하나입니다.** engram이 다루는 속성은 열넷입니다.

```yaml
---
type: concept              # 속성
artifact_stage: context    # 속성
sensitivity: internal      # 속성
---
```

각각이 문서를 한 가지 기준으로 가릅니다. `type`은 문서 종류로, `artifact_stage`는 성숙 단계로, `sensitivity`는 공개 범위로 가릅니다.

속성은 **켜거나 끕니다.**

- 켜면 그 필드가 단계별 필수 필드가 됩니다. 없으면 `lint`가 `frontmatter.missing-field`로 잡습니다.
- 끄면 그 필드를 쓰면 안 됩니다. 있으면 `lint`가 `schema.axis-off`로 잡습니다.

**프리셋은 어느 속성을 켤지 정하는 시작점입니다.** 열네 줄을 매번 쓰지 않게 해 주는 것뿐이고, 속성은 프리셋과 무관하게 `engram.yaml`에서 하나씩 켜고 끌 수 있습니다.

### 프리셋 셋

프리셋이 정하는 것은 속성뿐입니다. 디렉토리 구성, 게이트, 임계값은 셋 다 같습니다. 포함 관계라 오른쪽이 왼쪽을 전부 담습니다.

| 프리셋 | 켜지는 속성 | 더해지는 것 | 그래서 무엇이 되나 |
|---|---|---|---|
| `minimal` | 8 | `type`, `artifact_stage`, `status`, `indexable`, `tags`, `source_refs`, `derived_from`, `related` | 승급 파이프라인만 돕니다 |
| `personal` | 10 | `source_channel`, `derived_context` | 어디서 들어왔고 어디로 파생됐는지가 남습니다 |
| `team` | 14 | `scope`, `sensitivity`, `trigger_mode`, `workflow` | 업무 자료가 섞여도 반출 경계를 지킵니다. 자동화 기록이 남습니다 |

**실습은 `personal`로만 합니다.** 기본값이고, 교육이 끝난 뒤 자기 위키를 만들 때 쓰는 것도 `personal`입니다. **배운 구성과 쓰는 구성이 같습니다.** `minimal`은 `derived_context` 속성이 꺼져 있어서 4단계의 파생 왕복이 보이지 않고, `team`은 `sensitivity`와 `workflow`까지 필수라 3단계부터 채울 것이 늘어납니다. 프리셋을 실제로 바꾸는 것은 8단계에서 `migrate`로 해 봅니다.

출력이 만든 것을 그대로 알려 줍니다.

```
위키를 초기화했습니다: /Users/사용자/engram-wiki (프리셋: personal)

디렉토리:
  inbox/       새 자료가 들어오는 곳
  sources/     원본을 보존하는 곳
  context/     정리된 문서가 사는 곳
  archive/     승급에서 물러난 문서가 가는 곳

파일:
  engram.yaml  위키 설정. 속성과 임계값을 여기서 조정하세요
  index.md     첫 문서. 위키 소개로 채우세요
  .gitignore   .engram/ 캐시 디렉토리를 git에서 제외합니다
```

네 디렉토리를 소리 내어 읽습니다. **주제별로 나뉜 것이 아닙니다.** 같은 주제의 문서가 넷 중 어디에 있느냐가 그 문서의 성숙도입니다. 자료는 `inbox`로 들어와 `context`로 올라가고 수명이 끝나면 `archive`로 갑니다. `sources`는 원본을 그대로 두는 곳이라 이 흐름 옆에 붙어 있습니다.

## git 저장소로 만들기

```
git init -b main
git add -A
git commit -m "위키 시작"
```

**`-b main`을 반드시 붙입니다.** git 자체의 기본 브랜치 이름은 아직도 `master`입니다. GitHub가 `main`으로 바꾼 것은 GitHub에서 만든 저장소 이야기이고, 로컬 `git init`은 별개입니다. 그냥 `git init`을 치면 `master`가 생기고 아래 안내가 함께 나옵니다.

```
hint: Using 'master' as the name for the initial branch. This default branch name
hint: is subject to change. To configure the initial branch name to use in all
hint: of your new repositories, which will suppress this warning, call:
hint:
hint: 	git config --global init.defaultBranch <name>
```

git 버전 문제가 아닙니다. `init.defaultBranch` 설정이 비어 있으면 어느 버전이든 `master`를 씁니다. 한 번 정해 두면 이후 모든 저장소에 적용됩니다.

```
git config --global init.defaultBranch main
```

`-b` 플래그는 git 2.28부터 있습니다. 그보다 낮으면 `git branch -m main`으로 이름을 바꿉니다.

**위키는 git 저장소여야 합니다.** 세 가지 이유입니다.

- `engram.yaml`이 git으로 공유되기 때문에 팀이 같은 규칙을 씁니다. 6단계에서 만드는 `engram-state.yaml`도 마찬가지입니다.
- `doctor`의 점검 항목 두 개가 git 없이는 건너뛰어집니다.
- 8단계의 `sync`가 git 이력에서 날짜를 정정합니다. 그때 이력이 있으려면 지금부터 커밋이 쌓여야 합니다.

**각 단계가 끝날 때마다 커밋합니다.** 8단계에서 `sync`를 돌릴 때 그 커밋들이 재료가 됩니다.

`.gitignore`는 `init`이 만들어 뒀습니다. 안에는 `.engram/` 한 줄이 있습니다. 검색 색인은 언제든 다시 만들 수 있는 파생물이라 커밋하지 않습니다.

    조치: 슬러그에 대소문자만 다른 이름을 쓰지 마세요

```

**`fail 0`이면 통과입니다.** `env.fs-case` 경고는 macOS와 Windows에서 정상입니다. 그 파일시스템이 대소문자를 구분하지 않아서 `Go.md`와 `go.md`가 같은 파일이 됩니다. Linux에서는 이 줄이 `ok`로 나옵니다. 경고일 뿐이며 슬러그를 소문자로만 쓰면 걸릴 일이 없습니다.

`git init`을 하기 전에 돌리면 `env.git-autocrlf`와 `wiki.engram-gitignore`가 `skip`으로 나옵니다. 앞뒤로 한 번씩 돌려서 차이를 보게 하면 git이 왜 전제인지가 눈에 들어옵니다.

## 규칙 읽기

**이 단계의 핵심입니다.**

```
engram rules show
```

앞으로 여섯 단계에서 만날 것이 전부 여기 있습니다. 다 외우게 하지 않고 네 곳만 짚습니다.

**속성 14종.** `personal`은 열 개가 켜져 있습니다. 꺼진 속성을 문서에 쓰면 `lint`가 `schema.axis-off`로 잡습니다. 속성은 `engram.yaml`에서 하나씩 켜고 끌 수 있습니다.

**단계별 필수 필드.** 네 단계가 요구하는 것이 다릅니다. `context`가 `related`를 요구하고 `inbox`는 요구하지 않는 것이 이 체계의 요약입니다. **올라갈수록 자격이 늘어납니다.**

**승급 게이트.**

```
승급 게이트
  게이트가 승급을 거절하는 조건은 하나뿐입니다.
  문서가 위키에 실제로 있는 문서를 가리키는 고유 위키링크 수가 min_wikilinks 2개에 못 미치는 것입니다.
  없는 슬러그, 자기 자신, inbox 문서를 가리키는 링크는 세지 않습니다.
  promote와 new는 이것만 묻습니다. 길이도 형식도 주제도 막지 않습니다.
```

이 네 줄을 그대로 읽습니다. 4단계에서 거절을 직접 당하기 전에 왜 거절되는지를 미리 알려 둡니다. **막는 것이 하나뿐이라는 점이 요점입니다.** 나머지 판단은 사람에게 남습니다.

**lint 규칙 16종.** 훑기만 합니다. 심각도가 셋(`reject`, `error`, `warn`)이고 `reject`가 하나뿐이라는 것만 확인합니다.

```
engram status
```

```
현황
  inbox 0, source 0, context 0, archive 0 문서
  위키링크 0개, 고아 문서 0개
  lint: 파일 1개, error 0, warn 0, reject 0 (상세는 engram lint)

밀린 것 (기준 2026-08-17)
  inbox 문서 0개
  지금 승급할 수 있는 문서 0개

다음 행동
  - engram capture
    inbox가 비었습니다. 새 메모를 받아 파이프라인을 돌리세요
```

**`context 0`인데 `파일 1개`인 것을 짚습니다.** `index.md`는 루트 파일이라 단계 집계에 들어가지 않습니다. `engram.yaml`의 `root_files`가 그렇게 정하고 있습니다. 위키의 목차이지 승급 파이프라인을 지나는 문서가 아닙니다.

`다음 행동`이 `engram capture`를 가리킵니다. 3단계가 그것입니다. **`status`는 매 단계 끝에 돌립니다.** 도구가 다음에 뭘 하라고 하는지 보는 습관을 여기서 들입니다.

## index.md 채우기

`init`이 만든 `index.md`에는 자리를 채우는 문장이 들어 있습니다. 이것을 자기 위키 소개로 고칩니다. **에디터로 직접 엽니다.** 프론트매터는 건드리지 않고 `---` 아래 본문만 고칩니다.

두세 줄이면 됩니다. 무엇을 모으는 위키인지 씁니다.

고친 뒤 검사합니다.

```
engram lint
```

```
검사한 파일 1개, 위반 없음
```

손으로 고쳐도 `error 0`이어야 합니다. **도구가 만든 위키는 언제 `lint`를 돌려도 `error`가 0입니다.** 이 불변식을 매 단계 끝에서 확인합니다.

`updated` 필드가 옛 날짜로 남아 있는 것이 보입니다. 손으로 고쳤기 때문에 도구가 갱신할 기회가 없었습니다. 8단계의 `sync`가 git 이력에서 이런 것을 정정합니다. 지금은 그냥 둡니다.

## 확인

```
engram doctor      # fail 0
engram lint        # error 0
engram status      # 다음 행동이 engram capture
git log --oneline  # 커밋 하나 이상
```

넷이 통과하면 2단계가 끝납니다.

```
git add -A && git commit -m "index 소개 작성"
```

## 강사 노트

- 30분입니다. 절반을 `rules show`에 씁니다. 커맨드를 치는 시간보다 출력을 같이 읽는 시간이 길어야 합니다.
- `git init` 전후로 `doctor`를 한 번씩 돌리게 합니다. `skip` 두 개가 `ok`로 바뀌는 것을 눈으로 보면 설명이 필요 없습니다.
- 네 디렉토리를 두고 묻습니다. "지금 여러분 노트 앱의 폴더는 무엇으로 나뉘어 있습니까." 주제로 나뉜다는 답이 나오면 그 차이가 이 체계의 출발점이라고 말합니다.
- `min_wikilinks: 2`를 `engram.yaml`에서 직접 보게 합니다. 4단계에서 거절당할 때 이 숫자를 기억해야 합니다.
- 프리셋 셋을 비교하지 않습니다. 여기서 `minimal`과 `team`을 열어 보면 아직 쓰지 않은 속성 이야기로 빠집니다. 8단계까지 미룹니다.

## 이 단계에서 확정한 것

| 결정 | 내용 | 이유 |
|---|---|---|
| 위키 위치 | `~/engram-wiki` 하나 | 8단계까지 이것만 씁니다. 실습장을 늘리지 않습니다 |
| 프리셋 | `personal` 고정. 기본값이자 수료 후에도 쓰는 값 | `minimal`은 `derived_context` 속성이 꺼져 있어 4단계의 파생 왕복이 보이지 않고, `team`은 필수 필드가 많아 3단계부터 채울 것이 늘어납니다 |
| 용어 | 프론트매터 필드는 `속성`이라 부릅니다. `축`을 쓰지 않습니다 | 처음 만나는 사람이 무엇을 가리키는지 알 수 없습니다([0048](../decisions/0048-preset-names-follow-attribute-sets.md)) |
| 프리셋 비교 | 표로만 보여 주고 직접 만들어 보지 않습니다 | 셋을 다 만들면 아직 쓰지 않은 속성 이야기로 빠집니다. 8단계 `migrate`에서 실제로 바꿔 봅니다 |
| git | 2단계에서 `git init -b main`하고 매 단계 끝에 커밋합니다 | `doctor` 항목 둘이 git을 요구하고, 8단계 `sync`가 이력을 재료로 씁니다. `-b main`이 없으면 git 기본값인 `master`가 생깁니다 |
| `index.md` 편집 | 에디터로 본문만 고칩니다. `update` 커맨드를 쓰지 않습니다 | `update`는 4단계 커맨드입니다. 여기서 커맨드를 늘리지 않습니다 |
| 매 단계 마무리 | `doctor`, `lint`, `status` 셋을 돌리고 커밋합니다 | 불변식 확인을 습관으로 만듭니다 |

# 3단계. 넣기

## 목표

실습 재료를 자기 위키에 집어넣습니다. **원문을 고치지 않고 그대로 넣습니다.**

심는 문장은 이것입니다. **`capture`는 아무것도 검사하지 않습니다. 관문은 올라갈 때 한 번이면 됩니다.**

그래서 이 단계에서 하는 판단은 하나뿐입니다. **넣을 것인가 말 것인가.** 무엇을 남기고 무엇을 버릴지는 4단계에서 올릴 때 정합니다. 지금 정리하려 들면 관문이 두 번이 되고, 관문이 두 번이면 사람들은 아예 안 넣습니다.

## 재료

저장소의 `examples/materials/`에 넷이 있습니다. 1단계에서 클론한 곳입니다.

| 파일 | 무엇 |
|---|---|
| `회의-전사.txt` | 음성 회의를 STT로 돌린 결과. 화자 분리가 어긋나고 군더더기가 섞여 있습니다 |
| `기술문서-원문.md` | 외부 기술 블로그 글 전문 |
| `슬랙-스레드.txt` | 대화 로그 발췌. 성격이 다른 덩어리 셋이 섞여 있습니다 |
| `주간뉴스.txt` | 뉴스레터 한 통. **3단계에서 쓰지 않습니다.** 골라서 옮기는 일은 7단계 에이전트 심화에서 합니다 |

**전사는 engram의 일이 아닙니다.** 이 파일은 전사가 이미 끝난 결과입니다. engram은 음성을 다루지 않고 앞으로도 다루지 않습니다. 사용자가 자기 도구로 전사하고 그 결과 텍스트만 engram에 넣습니다.

### 두 디렉토리를 헷갈리지 않습니다

이름이 비슷해서 여기서 제일 많이 막힙니다.

| 무엇 | 어디 | 역할 |
|---|---|---|
| 실습 위키 | `~/engram-wiki` | **작업 위치.** 여기서 커맨드를 칩니다 |
| 저장소 | `~/engram` | 1단계에서 클론한 소스. **재료가 여기 있습니다** |

**복사하지 않고 경로로 읽습니다.** 이 단계의 커맨드는 전부 아래 두 줄을 깔고 시작합니다.

```
cd ~/engram-wiki                          # 작업 위치. 여기서 커맨드를 칩니다
MATERIALS=~/engram/examples/materials     # 실습 재료가 있는 디렉토리
```

**`MATERIALS`는 실습 재료 디렉토리를 담는 셸 변수입니다.** 매번 긴 경로를 치지 않으려고 둡니다. 클론을 홈이 아닌 곳에 했으면 이 줄만 자기 경로로 바꿉니다.

```
echo $MATERIALS     # /Users/사용자/engram/examples/materials
ls $MATERIALS       # 재료 넷과 README.md 가 보여야 합니다
```

**터미널을 새로 열면 사라집니다.** 다시 열었으면 위 두 줄을 다시 칩니다.

```
engram capture --title "..." < $MATERIALS/회의-전사.txt
```

`capture`와 `source`는 표준 입력을 받으므로 파일을 옮길 이유가 없습니다.

복사하면 어떻게 되는지 알아 두면 좋습니다. 실제로 확인한 결과입니다.

| 어디에 복사하면 | 무슨 일이 |
|---|---|
| `~/engram-wiki/materials/` | `lint`가 아예 무시합니다. `page_dirs`가 아니라서 순회 대상이 아닙니다. 위반은 안 나지만 정체불명 디렉토리가 위키에 남습니다 |
| `~/engram-wiki/inbox/` | **`error` 1이 납니다.** `기술문서-원문.md`에 프론트매터가 없어 `frontmatter.missing`입니다 |

재료는 위키가 아닙니다. 위키 안에 두지 않습니다.

### `--title`을 생략하면

`capture`와 `source`는 `--title`을 생략하면 **본문 첫 줄에서 제목을 만듭니다.** 문서 첫 줄이 `# 헤딩`이면 잘 나옵니다.

```
engram capture < $MATERIALS/기술문서-원문.md
inbox에 넣었습니다: .../2026-08-17-캐시-무효화를-설계하는-네-가지-방법.md
```

그런데 전사문 첫 줄은 이렇습니다.

```
[자동 전사 결과. 화자 분리 정확도 낮음. 검수 안 됨]
```

제목이 그대로 슬러그가 됩니다. **날것을 넣을 때는 `--title`을 줍니다.** 첫 줄이 무엇일지 사람이 보고 정하는 편이 낫습니다.

## 넣기 커맨드 둘

`capture`와 `source`는 넣는다는 점만 같고 성격이 정반대입니다.

```
engram capture --help
engram source --help
```

**두 플래그 목록을 나란히 보여 줍니다.** 여기가 이 단계의 핵심입니다.

| | `capture` | `source` |
|---|---|---|
| 플래그 | `--title`, `--slug`, `--wiki` | 위에 더해 `--created`, `--ref`, `--channel`, `--type` |
| 검사 | 없습니다 | 없습니다 |
| 들어가는 곳 | `inbox/` | `sources/` |
| 나중에 | 승급하면 **이동합니다**. 원본이 안 남습니다 | 승급하면 **파생을 만듭니다**. 원본이 그대로 남습니다 |

`capture`에는 `--channel`조차 없습니다. 받는 자리를 최대한 가볍게 두었기 때문입니다. 반대로 `source`는 **원본을 확정하는 자리**라 출처와 날짜를 받습니다. 이후 본문을 고치지 않는 것이 계약입니다.

## 실습 1. 회의 전사

`회의-전사.txt`를 엽니다. 42분짜리 회의이고 결론이 없습니다. 가설 셋이 나오고 각자 할 일을 나눈 채 끝납니다.

**요약하지 않습니다. 통째로 넣습니다.**

```
cd ~/engram-wiki
MATERIALS=~/engram/examples/materials

engram capture --title "응답 지연 회의 전사" < $MATERIALS/회의-전사.txt
```

```
inbox에 넣었습니다: /Users/사용자/engram-wiki/inbox/2026-08-17-응답-지연-회의-전사.md
다음: 문서를 정리한 뒤 승급하세요. 지금은 engram lint로 위키 상태를 볼 수 있습니다
```

손으로 요약해서 넣고 싶은 충동이 들 것입니다. 참습니다. **`inbox`는 검수된 곳이 아니라 받는 곳입니다.** 정리는 4단계에서 올릴 때 합니다. 지금 정리하면 관문이 두 번이 되고, 그러면 사람들은 아예 안 넣게 됩니다. 실습 3의 슬랙 로그가 그 이야기를 합니다.

만들어진 파일을 엽니다.

```yaml
---
type: inbox-note
artifact_stage: inbox
status: inbox
source_channel:
indexable: false
created: 2026-08-17
---
```

**필수 속성이 다섯뿐입니다.** 2단계에서 `rules show`로 본 그 목록입니다. `inbox`는 가장 적게 요구합니다.

전사문에서 결정된 것은 "캐시 보류"와 "각자 확인할 것 셋"뿐이고 나머지는 전부 가설입니다. **그 구분은 지금 하지 않습니다.** 4단계에서 정합니다. 그때 이 문서는 지식이 아니라 **증거**로 판정되어 `sources`로 갑니다.

## 실습 2. 원본 보존

`기술문서-원문.md`는 남의 글입니다. 요약하지 않고 그대로 보존합니다.

```
engram source \
  --type source-raw \
  --title "캐시 무효화를 설계하는 네 가지 방법" \
  --created 2026-02-18 \
  --channel web \
  --ref "https://example.com/cache-invalidation" \
  < $MATERIALS/기술문서-원문.md
```

### sources 에는 원본과 정제본이 함께 옵니다

여기가 이 단계에서 제일 헷갈리는 자리입니다.

`sources`는 **지식이 아니라 증거**입니다. `context`가 주장하는 것이 맞는지 나중에 확인하려면 근거가 그 자리에 있어야 합니다. 그래서 잘 쓴 문서일 필요가 없습니다.

두 가지가 들어옵니다.

| `type` | 무엇 | 누가 만드나 |
|---|---|---|
| `source-raw` | **원문 그대로.** 손대지 않았습니다 | 사람이 파일을 그대로 넣습니다 |
| `source-summary` | **정제본.** 읽고 추린 결과 | 사람 또는 에이전트가 만듭니다 |

디렉토리를 나누지 않습니다. `sources/` 하나에 두고 `type`이 어느 쪽인지 말합니다. 디렉토리는 성숙 단계를 뜻하지 종류를 뜻하지 않습니다.

**`--type`의 기본값은 `source-summary`입니다.** 실제 위키에서 정제본이 훨씬 흔하기 때문입니다. 지금은 원문을 그대로 넣으므로 `--type source-raw`를 명시했습니다. **안 주면 원문에 "요약"이라는 종류가 붙어 프론트매터가 거짓이 됩니다.**

정제본을 만드는 것은 engram의 일이 아닙니다. engram에 요약 기능이 없습니다. 사람이 읽고 쓰거나 에이전트가 만들어 넣습니다. 근거는 [ADR 0051](../decisions/0051-sources-holds-originals-and-refined-summaries.md)에 있습니다.

표준 입력으로 파일을 통째로 넣습니다. `capture`도 같은 방식을 받습니다.

**`--created`, `--channel`, `--ref`는 전부 선택입니다.** 안 줘도 들어가고 `lint`도 통과합니다. 그런데 주는 편이 낫습니다.

| 생략하면 | 무슨 일이 |
|---|---|
| `--created` | 오늘 날짜가 됩니다. 2월에 쓰인 글이 8월 것이 되어 6단계 재발견이 신선도를 잘못 봅니다 |
| `--ref` | `source_refs: []`. 출처 없는 원본 보존은 반쪽입니다 |
| `--channel` | 빈 값으로 남습니다. 어디서 들어왔는지가 사라집니다 |

**필수 필드 검사는 키가 있는지만 봅니다.** 값이 비어 있어도 통과합니다. 채우는 것은 규칙이 아니라 판단입니다.

### 이 셋은 왜 사람이 채우나

CLI라서가 아닙니다. **사실이어야 하는 값**이기 때문입니다.

원본이 언제 쓰였는지는 파일 안에 안 적혀 있는 경우가 많습니다. 짐작해서 채우면 위키가 틀린 출처를 사실로 갖게 됩니다. 그래서 `--created`는 `2026-02`처럼 연월까지만 주는 것도 허용합니다. **모르는 날짜를 지어내게 만드는 스키마는 데이터를 오염시킵니다.**

4단계에서 붙일 에이전트도 이 값을 대신 채우지 않습니다. 스킬 문서가 이렇게 지시합니다.

```
원문을 오래 보존할 값어치가 있어 보이면 사람에게 이렇게 제안하고 멈춘다.
네가 실행하지 않는다.

    engram source --title <제목> --created <원본 작성일> --ref <출처> < 원문파일

--created 는 원본이 쓰인 날이고 --ref 는 출처다. 둘 다 사실이어야
하며 그 확인은 사람이 한다.
```

**MCP 도구 목록에는 `source`가 아예 없습니다.** 쓰기 도구는 `capture` 하나뿐입니다([ADR 0043](../decisions/0043-mcp-exposes-one-write-tool-and-omits-promote.md)). 에이전트가 쓸 수 있는 곳은 `inbox`까지입니다.

그래서 실무 흐름은 이렇게 나뉩니다. **에이전트가 원문을 `capture`로 `inbox`에 넣고, 원본으로 확정할지는 사람이 `source`로 정합니다.** 원본이 사라지지 않는 결과는 같고 확정하는 주체가 다릅니다.

```
source에 넣었습니다: /Users/사용자/engram-wiki/sources/2026-02-18-캐시-무효화를-설계하는-네-가지-방법.md
다음: 정리가 끝나면 이 원본을 인용하는 맥락 문서를 만드세요
```

**파일명 날짜가 오늘이 아닙니다.** `--created`로 준 2026-02-18입니다. 프론트매터를 봅니다.

```yaml
created: 2026-02-18      # 원본이 쓰인 날
sourced_at: 2026-08-17   # 내 위키에 들어온 날
```

**날짜가 둘로 갈려 있습니다.** 수년 전 자료를 옮겨 올 때 편입일만 남기면 그것이 오래된 자료라는 사실이 사라지고, 작성일만 남기면 내 위키가 언제부터 그것을 알았는지 모릅니다. `sources/`에는 세 번째 날짜인 `updated`가 없습니다. 원본은 갱신되지 않기 때문입니다.

`--created`를 생략하면 오늘이 됩니다. 연월까지만 아는 자료는 `--created 2026-02`도 됩니다. **모르는 날짜를 지어내게 만드는 스키마는 데이터를 오염시킵니다.**

## 실습 3. 슬랙 로그

`슬랙-스레드.txt`를 엽니다. 시간 순으로 흐르지만 **성격이 다른 덩어리 셋**입니다.

- 09:41부터 09:54: 배포가 실패한 원인
- 11:20부터 11:28: 기록이 안 쌓이는 이유
- 14:05부터 14:07: 조치 완료

**여기서는 하나만 정합니다. 통째로 넣을지 나눌지입니다.** 내용을 다시 쓰지 않습니다.

통째로 넣는 쪽입니다.

```
engram capture --title "배포 실패 스레드" < $MATERIALS/슬랙-스레드.txt
```

나누는 쪽이면 파일을 잘라 세 번 넣습니다. 어느 쪽이든 **원문을 고치지 않습니다.**

나중에 검색으로 꺼낼 때 한 덩어리에 세 주제가 섞여 있으면 어느 것으로도 잘 안 걸립니다. 그 불편은 5단계에서 직접 겪습니다. 지금 정답을 정해 주지 않습니다.

세 번째 메모를 소리 내어 읽습니다. **로그 속 사람들이 방금 이 도구가 푸는 문제를 스스로 말하고 있습니다.** 대충 던지는 곳과 정리된 곳이 나뉘어 있지 않아서 아예 안 적게 된다는 것입니다. 그것이 `inbox`와 `context`가 나뉜 이유입니다.

## 실제로는 이 자리에 에이전트가 섭니다

여기까지 손으로 했습니다. **실무에서는 이 자리를 에이전트가 대신합니다.**

```
회의 전사 파일을 읽고 engram capture 로 내 위키 inbox 에 넣어 줘
```

에이전트가 파일을 읽고 `engram capture`를 부릅니다. 사람이 제목을 짓거나 터미널에 긴 문자열을 치지 않습니다. **바로 다음 4단계에서 실제로 붙입니다.**

**그러면 왜 지금 손으로 하는가.** 커맨드 한 줄이라 30초면 끝나고, 에이전트가 무엇을 부르는지 알아야 4단계에서 그 제안을 검토할 수 있기 때문입니다. `skills install`이 심는 스킬 문서가 에이전트에게 이렇게 말합니다.

```
네가 쓸 수 있는 곳은 inbox까지다. 새 자료는 capture로 inbox에 넣는다.
context로 올리는 일은 승급 게이트를 지나야 하고 확정은 사람이 한다.
promote를 제안할 수 있지만 실행은 사람에게 맡겨라.
```

`capture`에 플래그가 셋뿐인 것도 여기서 설명됩니다. **에이전트가 쓰는 자리라 좁게 뒀습니다.** 넓히면 에이전트가 분류와 판정까지 하게 되고, 그러면 위키가 사람 손을 떠납니다.

그리고 engram은 요약하지 않습니다. 스킬 문서의 첫 문단이 그렇게 못 박습니다.

```
engram은 LLM을 부르지 않는다. 네가 engram을 부른다.
engram에게 요약이나 판단을 시키려 하지 마라.
```

요약이 필요하면 **에이전트가 하고 그 결과를 engram에 넣습니다.** engram 안에 요약 기능을 넣지 않은 것이 이 제품의 경계입니다.

## 확인

```
ls inbox sources
engram lint
engram status
```

```
검사한 파일 4개, error 0, warn 2, reject 0
```

**`warn` 둘이 정상입니다.** 전부 `graph.orphan`이며 방금 넣은 `inbox` 문서가 아무와도 이어져 있지 않다는 뜻입니다. 아직 이을 곳이 없으니 당연합니다. **`error`와 `reject`가 0인지만 봅니다.**

```
밀린 것 (기준 2026-08-17)
  inbox 문서 2개, 전부 오늘 들어왔습니다
  지금 승급할 수 있는 문서 0개

다음 행동
  - 링크 채우기
    inbox 문서 2개가 있지만 지금 올릴 수 있는 것이 없습니다. 승급하려면
    문서마다 위키에 있는 문서를 가리키는 링크가 2개 필요합니다. promote 할 때 --related 로 채울 수 있습니다
```

**도구가 다음 단계를 정확히 가리킵니다.** 4단계가 그것입니다.

```
git add -A && git commit -m "3단계: 재료를 inbox와 sources에 넣음"
```

## 강사 노트

- 40분입니다. 커맨드를 치는 시간보다 재료를 읽는 시간이 길어야 합니다.
- **실습 1을 마치고 만들어진 문서를 열어 보게 합니다.** 68줄 전사문이 그대로 들어가 있습니다. 요약하고 싶었던 사람이 대부분입니다. 왜 참았는지를 한 번 더 말합니다. 관문은 올라갈 때 한 번입니다.
- `capture`의 플래그가 셋뿐이라는 것을 반드시 짚습니다. 수강생은 보통 분류를 먼저 하려고 합니다. 여기서는 못 합니다. 그것이 설계입니다.
- 슬랙 로그를 하나로 넣은 수강생이 나오면 그대로 둡니다. 5단계 검색에서 스스로 불편을 겪게 하는 편이 낫습니다.

## 이 단계에서 확정한 것

| 결정 | 내용 | 이유 |
|---|---|---|
| 재료 | `examples/materials/` 넷. 전부 합성 자료 | 저장소가 공개 예정이라 조직 식별자를 넣지 않습니다 |
| 재료의 성격 | 정리된 요약이 아니라 날것 | 요약을 주면 복사해 붙이고 끝나서 판단 실습이 사라집니다 |
| 전사 | engram이 하지 않습니다. 전사 결과 텍스트만 받습니다 | 여정 2는 바이너리 밖 동선입니다 |
| 넣는 방식 | **원문을 그대로 넣습니다.** 손으로 요약하지 않습니다 | `inbox`는 받는 곳이지 검수된 곳이 아닙니다. 여기서 정리를 시키면 관문이 두 번이 되고 도구의 논지가 무너집니다 |
| 이 단계의 판단 | 넣느냐 마느냐, 통째로냐 나누느냐 둘뿐입니다 | 요약 판단은 4단계 승급으로 옮깁니다 |
| 에이전트 | 3단계 끝에서 **실무에서는 에이전트가 이 자리에 선다**고 밝히고 4단계에서 실제로 붙입니다 | 손으로만 보여 주면 제품을 잘못 이해합니다. `capture` 는 에이전트의 쓰기 표면입니다 |
| 잘못 넣은 것 | 그 자리에서 고치지 않습니다 | 5단계 검색과 4단계 승급에서 스스로 겪게 합니다 |

# 4단계. 올리기

## 목표

3단계에서 던져 넣은 것을 `context`로 올립니다. **여기가 관문입니다.**

심는 문장은 둘입니다.

- **거절 사유는 하나뿐입니다.** 거절 경험이 곧 교육입니다.
- **정리도 실행도 에이전트가 하고 사람은 읽고 승인합니다.** 사람이 문장을 쓰거나 커맨드를 치는 자리가 아닙니다.

## 이 단계부터 표기가 갈립니다

3단계까지는 전부 사람이 쳤습니다. **4단계부터 에이전트가 들어오므로 누가 무엇을 하는지 표기로 구분합니다.** 5단계 이후도 같습니다.

| 표기 | 뜻 |
|---|---|
| **터미널** | 사람이 터미널에 칩니다 |
| **에이전트에게** | 에이전트 대화창에 말합니다. 커맨드가 아닙니다 |
| 인용절 안의 커맨드 | **에이전트가 부릅니다. 사람은 치지 않습니다.** 무슨 일이 일어나는지 알라고 적었습니다 |

사람이 터미널에 치는 것은 설치와 확인, 그리고 `mv`와 `archive`뿐입니다. **승급 자체는 에이전트가 승인을 받고 실행합니다.**

## 1. 먼저 거절당합니다

3단계에서 넣은 슬랙 로그를 그대로 올려 봅니다.

**터미널**

```
cd ~/engram-wiki
engram promote inbox/2026-08-17-배포-실패-스레드.md --type incident
```

```
Error: 승급 게이트를 넘지 못했습니다: 이어지는 위키링크가 0개로 min_wikilinks 2개에 못 미칩니다
위키에 있는 문서를 가리키는 링크를 2개 더 추가하세요. 없는 슬러그와 inbox 문서는 세지 않습니다
이 자리에서 채우려면 --related <슬러그>를 반복해 주세요
```

**막힌 이유가 하나입니다.** 길이도, 형식도, 주제도 묻지 않았습니다. 문서 종류가 `incident`가 맞는지도 안 따졌습니다. 이 문서가 위키의 다른 무엇과도 이어져 있지 않다는 것만 막았습니다.

2단계 `rules show`에서 읽은 네 줄이 여기서 실물이 됩니다.

> 게이트가 승급을 거절하는 조건은 하나뿐입니다.
> 문서가 위키에 실제로 있는 문서를 가리키는 고유 위키링크 수가 min_wikilinks 2개에 못 미치는 것입니다.
> 없는 슬러그, 자기 자신, inbox 문서를 가리키는 링크는 세지 않습니다.
> promote와 new는 이것만 묻습니다. 길이도 형식도 주제도 막지 않습니다.

**메시지 마지막 줄은 지금 따르지 않습니다.** `--related`를 두 번 줘서 그 자리에서 통과시킬 수 있지만, 그러면 대화 로그가 정리 없이 그대로 `context`에 올라갑니다. 관문에서 정리하는 것이 이 단계의 요점입니다.

**이것을 손으로 푸는 것은 이 도구의 사용법이 아닙니다.** 로그를 읽고, 남길 것을 정하고, 이을 문서를 찾고, 슬러그를 짓는 일입니다. 그 일을 사람이 하면 3단계에서 없앤 관문이 여기서 되살아납니다.

## 2. 에이전트를 붙입니다

**터미널**

```
engram skills install --dry-run
```

```
심을 예정인 파일 2개 (dry-run. 아직 쓰지 않았습니다)
  /Users/사용자/.claude/skills/engram/SKILL.md
  /Users/사용자/.agents/skills/engram/SKILL.md
에이전트를 다시 시작해야 스킬이 잡힐 수 있습니다
```

**홈을 건드리므로 먼저 봅니다.** 실제로 있는 스킬 디렉토리를 찾아 전부에 심고, 없는 도구를 위해 디렉토리를 만들지 않습니다.

### 전역이냐 이 위키만이냐

| | 전역 (기본값) | 이 위키만 |
|---|---|---|
| 커맨드 | `engram skills install` | `engram skills install --dir <프로젝트>/.claude/skills` |
| 심는 곳 | `~/.claude/skills/engram/` | `<프로젝트>/.claude/skills/engram/` |
| 언제 | 위키를 실제로 쓰기 시작했을 때 | **기능을 검증하거나 시험해 볼 때** |

전역이 기본값인 이유는 **스킬 문서가 위키와 무관하기 때문**입니다. 임계값이나 허용값을 담지 않아 위키가 몇 개든 하나면 되고, 위키 밖에서 에이전트를 띄웠을 때도 필요합니다. 회의 노트가 있는 다른 폴더에서 "이거 위키에 넣어 줘"가 되어야 합니다.

지울 때는 디렉토리를 지웁니다. 전용 커맨드는 없습니다.

```
rm -rf ~/.claude/skills/engram
```

**실습에서는 전역으로 갑니다.** 8단계까지 쓰고 그 뒤로도 쓰기 때문입니다.

**터미널**

```
engram skills install
engram reindex
```

```
심었습니다 2개
  /Users/사용자/.claude/skills/engram/SKILL.md
  /Users/사용자/.agents/skills/engram/SKILL.md
에이전트를 다시 시작해야 스킬이 잡힐 수 있습니다
```

`reindex`는 검색 색인을 만듭니다. 없어도 검색은 되지만 매번 전체를 읽습니다.

### 심은 문서를 읽습니다

**터미널**

```
cat ~/.claude/skills/engram/SKILL.md
```

**여기가 이 과정에서 제일 중요한 페이지입니다.** 에이전트가 무엇을 할 수 있고 무엇을 못 하는지가 전부 여기 있습니다.

> 네가 쓸 수 있는 곳은 inbox까지다. 새 자료는 capture로 inbox에 넣고
> inbox 문서의 본문은 update로 고칠 수 있다. 그 안에서는 자유롭게 하라.
> context로 올리는 일은 승급 게이트를 지나야 하고 확정은 사람이 한다.
> promote를 제안할 수 있지만 실행은 사람에게 맡겨라.

**에이전트를 다시 시작합니다.**

## 3. 에이전트에게 시킵니다

**에이전트에게**

```
~/engram-wiki 의 inbox 에 있는 배포 실패 스레드를 승급할 수 있게 준비해 줘
```

**커맨드를 알려 주지 않습니다.** 스킬 문서가 순서를 지시합니다.

에이전트가 넷을 하고 **그중 두 번 사람에게 묻습니다.** 아래 커맨드는 전부 에이전트가 부르는 것이고 사람은 치지 않습니다.

> **이을 곳을 찾습니다.** 사람에게 묻지 않고 검색합니다.
>
> `engram search "배포 설정" --json --wiki ~/engram-wiki`
>
> **이미 있는 문서만 고릅니다.** 게이트는 실재하는 대상을 가리키는 링크만 셉니다. 지금 위키에 있는 것은 색인과 `sources`의 기술문서 원본뿐이라 그 둘을 씁니다.
>
> `path`가 `inbox/`로 시작하는 것은 뺍니다. 그 문서가 승급될 때 날짜 접두사가 떨어져 링크가 깨지기 때문입니다.

> **본문을 정리하고, 갈아 끼우기 전에 묻습니다.** 로그를 읽고 남을 것만 씁니다. 성격이 다른 덩어리 셋 중 무엇을 남길지가 판단입니다. 본문에 `[[2026-02-18-캐시-무효화를-설계하는-네-가지-방법]]`을 심습니다. `sources`의 원본이고 **슬러그에 날짜 접두사가 붙어 있습니다.**
>
> **여기가 되돌릴 수 없는 자리입니다.** `update`는 본문을 통째로 바꿔서 원문이 사라집니다. 정리한 본문을 보여 주고 **승인을 받은 뒤에** 실행합니다. 이것이 첫 번째 물음입니다.
>
> `engram update inbox/2026-08-17-배포-실패-스레드.md --body-from <임시파일> --wiki ~/engram-wiki`

> **`--dry-run`으로 스스로 검증합니다.** 통과할 때까지 사람에게 아무것도 묻지 않습니다.
>
> `engram promote ... --type incident --slug 설정-키-누락-사건 --related index --dry-run`
>
> ```
> 올릴 예정입니다: inbox/2026-08-17-배포-실패-스레드.md에서 context/설정-키-누락-사건.md로
> 문서 종류: incident
> 게이트: 링크 2개, 대상 2개, 기준 2개
> 시험 실행이라 아무것도 쓰지 않았습니다
> ```
>
> **게이트 통과 여부는 짐작하지 않습니다.** 아무것도 쓰지 않으니 몇 번이든 돌릴 수 있고, 거절당하면 `--related`를 고쳐 다시 돌립니다.

> **승인을 받고 실행합니다.** 통과한 뒤 셋을 보여 줍니다. 올라갈 슬러그와 종류, 무엇에 이어지는지, **`inbox` 원본이 사라진다는 사실**입니다. 이것이 두 번째 물음입니다.
>
> 승인을 받으면 `--dry-run`만 떼고 실행한 뒤 `lint`를 돌려 보고합니다.
>
> ```
> context로 올렸습니다: context/설정-키-누락-사건.md
> 문서 종류: incident
> 게이트: 링크 2개, 대상 2개, 기준 2개
> ```

## 4. 사람이 결정합니다

**커맨드를 치지 않습니다. 승인만 합니다.** 에이전트가 두 번 묻고 그 둘이 이 단계에서 사람이 하는 일 전부입니다.

| 언제 | 무엇을 판단하나 |
|---|---|
| 갈아 끼우기 전 | **원문을 지워도 되는가.** 대화 로그가 사라집니다. 되돌릴 수 없습니다 |
| 승급 전 | **올릴 값어치가 있는가.** `context`는 검수된 지식의 자리입니다 |

**승인 전에 정리본을 반드시 읽습니다.** 여기가 요점입니다. 읽지 않고 "응"만 하면 게이트의 사람 확인은 형식만 남습니다.

| 볼 것 | 아니면 |
|---|---|
| **틀린 말이 들어갔는가** | 에이전트가 대화 속 제안을 결정처럼 적기 쉽습니다 |
| **버릴 것을 버렸는가** | 세 덩어리 중 무엇이 남았는지 봅니다 |
| **링크가 맞는가** | 억지로 이은 링크는 나중에 검색을 더럽힙니다 |

**문장을 다시 쓰지 않습니다.** 마음에 안 들면 에이전트에게 무엇이 틀렸는지 말하고 다시 시킵니다. **그게 판단이고, 커맨드를 치는 것은 판단이 아닙니다.**

**터미널**

```
ls inbox
```

```
2026-08-17-응답-지연-회의-전사.md
```

**슬랙 문서가 없습니다. `inbox` 문서는 승급하면 이동합니다.** 파일명의 날짜 접두사도 떨어졌습니다. `context` 문서는 날짜로 부르지 않기 때문입니다.

## 5. 전사는 증거입니다

`inbox`에 회의 전사가 남았습니다. **이것은 지식이 아닙니다.**

upstream `inbox/README.md`가 `inbox`의 탈출 경로를 셋으로 정합니다.

```
- delete the inbox item if it has no long-term value
- move evidence to sources/ if it should be traceable
- promote durable knowledge to context/
```

| 길 | 언제 | 커맨드 |
|---|---|---|
| 삭제 | 오래 둘 값어치가 없다 | 파일을 지웁니다 |
| `sources`로 | **나중에 추적 가능해야 한다** | `promote --to sources` |
| `context`로 | 재사용될 지식이다 | `promote` (방금 슬랙에 한 것) |

**전사가 가운데 자리입니다.** 자동 전사라 화자 귀속이 확정이 아니고, "그 결정이 정말 그 회의에서 나왔나"를 나중에 확인하려면 원문이 있어야 합니다. `sources`는 **지식이 아니라 증거**입니다.

**에이전트에게**

```
inbox 에 남은 회의 전사는 증거로 남겨 줘. 회의는 2026-03-04 였어
```

> **에이전트가 이렇게 제안하고 멈춥니다.**
>
> `engram promote inbox/2026-08-17-응답-지연-회의-전사.md --to sources --created 2026-03-04 --ref "회의 전사" --channel teams --wiki ~/engram-wiki`
>
> ```
> sources로 옮겼습니다: sources/2026-03-04-응답-지연-회의-전사.md
> 문서 종류: source-raw
> 원본은 이후 본문을 고치지 않습니다. 다음: 이 원본을 인용하는 맥락 문서를 만드세요
> ```

**셋이 다릅니다.**

| | `--to sources` | `promote` (context로) |
|---|---|---|
| 본문 | **그대로 둡니다.** 원본 보존이 계약입니다 | 정리해서 갈아 끼웁니다 |
| 게이트 | **적용하지 않습니다.** 증거는 고립돼도 값어치가 있습니다 | 링크 2개를 요구합니다 |
| `type` 기본값 | `source-raw` | 지정해야 합니다 |

**파일명 날짜가 `--created`입니다.** 회의가 열린 2026-03-04이지 오늘이 아닙니다. `--created`와 `--ref`는 **사실이어야 하고 그 확인은 사람이 합니다.** 에이전트가 회의 날짜를 물어본 이유입니다.

**`inbox`가 비었습니다.**

**터미널**

```
ls inbox sources
```

## 6. 원본에서 파생을 만듭니다

`sources`에 둘이 있습니다. 3단계에서 넣은 기술문서와 방금 옮긴 전사입니다. 기술문서를 지식으로 만듭니다.

**에이전트에게**

```
sources 의 캐시 무효화 원본을 승급할 수 있게 준비해 줘
```

> `engram promote sources/2026-02-18-캐시-무효화를-설계하는-네-가지-방법.md --type concept --slug 캐시-무효화-정리 --related index --related 설정-키-누락-사건`
>
> ```
> context로 올렸습니다: context/캐시-무효화-정리.md
> 문서 종류: concept
> 게이트: 링크 2개, 대상 3개, 기준 2개
> ```

**터미널**

```
ls sources
```

```
2026-02-18-캐시-무효화를-설계하는-네-가지-방법.md
2026-03-04-응답-지연-회의-전사.md
```

**원본이 그대로 있습니다.** `inbox`는 이동했는데 `sources`는 남았습니다. **여기가 `inbox`와 `sources`의 가장 큰 차이입니다.**

만들어진 것은 **파생 문서**입니다. 양쪽 프론트매터가 서로를 가리킵니다.

```yaml
# sources/2026-02-18-캐시-무효화를-설계하는-네-가지-방법.md
derived_context:
  - 캐시-무효화-정리

# context/캐시-무효화-정리.md
derived_from:
  - sources/2026-02-18-캐시-무효화를-설계하는-네-가지-방법.md
```

나중에 `context` 문서의 주장이 맞는지 확인하려면 이 링크를 따라가면 됩니다. **`sources`가 증거인 이유가 여기서 보입니다.**

### 세 자료가 세 길로 갔습니다

| 자료 | 3단계 | 4단계 |
|---|---|---|
| 기술문서 원문 | `source`로 `sources`에 직행 | `promote`로 파생. **원본 남음** |
| 슬랙 스레드 | `capture`로 `inbox` | 정리해서 `context`로. **원본 사라짐** |
| 회의 전사 | `capture`로 `inbox` | `--to sources`로 증거 보존. **본문 그대로** |

**기술문서는 왜 3단계에서 바로 `sources`로 갔나.** 남의 글이고 URL과 작성일이 있어 **넣는 시점에 이미 증거임이 확실**했기 때문입니다. 전사는 우리 것이고 남길지 애매하니 일단 `inbox`로 받고 여기서 정했습니다. **`inbox`는 판단이 안 끝난 것의 자리입니다.**

## 7. index.md는 저절로 안 바뀝니다

여기서 대부분 한 번 묻습니다. **문서를 올렸는데 `index.md`가 그대로입니다.**

`--related index`는 **새 문서에서 색인으로 나가는** 링크입니다. 반대 방향은 만들지 않습니다. **engram은 `index.md`를 자동으로 고치지 않습니다.** `init`이 만들고, 그 뒤로는 사람이나 에이전트가 `update`로 씁니다.

대신 조회로 봅니다.

**터미널**

```
engram backlinks index
```

```
archive/배포-설정-키-사건.md:11  related 필드  [[index]]
context/캐시-무효화-정리.md:13  related 필드  [[index]]
```

**자동으로 채우지 않는 이유가 있습니다.** `index.md`가 모든 문서를 가리키면 **고아 판정이 영원히 0이 됩니다.** 색인에서 들어오는 링크도 링크로 세기 때문입니다.

| `index.md`가 | `lint`가 그 문서를 |
|---|---|
| 안 가리킴 | `graph.orphan` 경고 |
| `[[슬러그]]`로 가리킴 | 경고 없음 |

승급할 때마다 색인에 한 줄씩 붙이면 **아무 데도 안 이어진 문서를 찾아낼 방법이 사라집니다.** 승급 게이트는 그대로 막습니다. 게이트는 문서 자신이 나가는 링크만 세기 때문입니다. **무력화되는 것은 고아 판정 쪽입니다.**

## 8. 이름 바꾸기와 폐기하기

**이 둘은 에이전트에게 주지 않습니다.** `mv`는 여러 파일을 한 번에 고치고 `archive`는 단계를 옮깁니다. 스킬 문서가 단계 이동 커맨드를 사람의 것으로 남겨 둔 이유입니다.

**먼저 시험 실행합니다.**

**터미널**

```
engram mv 설정-키-누락-사건 배포-설정-키-사건 --dry-run
```

```
바꿀 예정입니다: context/설정-키-누락-사건.md에서 context/배포-설정-키-사건.md로 (슬러그 배포-설정-키-사건)
고친 링크 1건:
  context/캐시-무효화-정리.md: 1건
시험 실행이라 아무것도 쓰지 않았습니다
```

**무엇이 바뀌는지 먼저 보고 실행합니다.** 본문 위키링크와 프론트매터 `related`를 함께 고칩니다. 코드 블록 안의 링크 문법은 건드리지 않습니다.

**터미널**

```
engram mv 설정-키-누락-사건 배포-설정-키-사건
engram archive context/배포-설정-키-사건.md
```

```
옮겼습니다: context/설정-키-누락-사건.md에서 context/배포-설정-키-사건.md로 (슬러그 배포-설정-키-사건)
고친 링크 1건:
  context/캐시-무효화-정리.md: 1건

알림: 이 문서를 가리키는 링크 1개가 있습니다. 링크는 깨지지 않고 가리키는 대상이 폐기 상태가 됩니다
보관했습니다: archive/배포-설정-키-사건.md
슬러그 배포-설정-키-사건는 유지됩니다. 들어오는 링크는 깨지지 않습니다
이 문서를 가리키던 링크 1개가 폐기 상태를 가리키게 됩니다
```

**폐기해도 슬러그가 그대로입니다.** 그 사건을 가리키던 링크가 깨지지 않습니다. 지웠다면 다른 문서에 구멍이 생깁니다. 이력이 남는 것이 요점입니다.

`demote`도 있습니다. 잘못 올렸을 때 `inbox`나 `sources`로 되돌립니다. 다만 되돌리면 파일명에 날짜 접두사가 붙어 슬러그가 바뀌고 **그 문서를 가리키던 링크가 깨집니다.** 커맨드가 실행 전에 그 목록을 경고로 냅니다.

## 9. 확인

**터미널**

```
engram lint
engram status
git add -A && git commit -m "4단계: 에이전트 연결, 승급, 증거 보존, 보관"
```

```
검사한 파일 5개, 위반 없음
```

```
현황
  inbox 0, source 2, context 1, archive 1 문서
  위키링크 4개, 고아 문서 0개
  lint: 파일 5개, error 0, warn 0, reject 0 (상세는 engram lint)
```

**`inbox`가 비었습니다.** 3단계 끝에서 `inbox 2, source 1, context 0`이던 것이 여기까지 왔습니다. `source`가 둘로 늘어난 것이 전사를 증거로 남긴 결과입니다.

**고아 문서가 2개에서 0개가 되었습니다.** 게이트가 그것을 강제한 결과입니다.

## 이 단계에서 누가 무엇을 했나

커맨드를 몇 개 쳤는지가 아니라 **무엇을 판단했는지**를 봅니다.

| 사람 | 에이전트 |
|---|---|
| 원문을 지워도 되는지 정했습니다 | 원문을 읽고 정리했습니다 |
| 정리본에 틀린 말이 없는지 봤습니다 | 이을 곳을 검색으로 찾았습니다 |
| 올릴 값어치가 있는지 정했습니다 | `--dry-run`으로 스스로 검증했습니다 |
| 전사를 증거로 남기기로 정했습니다 | 승인받고 `promote`를 실행했습니다 |
| 회의 날짜를 확인해 줬습니다 | `--to sources`로 증거를 옮겼습니다 |
| 이름을 바꾸고 폐기했습니다 | |

**문장을 쓴 사람도, 커맨드를 친 사람도 없습니다.** 사람이 한 것은 읽고 판단한 것뿐입니다. 그것이 설계입니다. 게이트가 지키는 것은 문장의 품질이 아니라 연결이고, 사람이 지키는 것은 그것을 올릴 값어치가 있는가입니다.

## 강사 노트

- 70분입니다. 거절 15분, 에이전트 연결 15분, 승급과 검토 25분, 증거 보존 15분입니다.
- **거절 메시지를 소리 내어 읽힙니다.** 무엇이 막혔는지, 무엇은 안 막혔는지 둘 다 말하게 합니다.
- **거절 직후에 "이걸 손으로 풀어 보겠느냐"고 묻습니다.** 대화 로그를 읽고 정리하겠다는 사람은 없습니다. 그 침묵이 에이전트를 붙이는 이유입니다.
- **6절의 세 자료 표가 이 단계의 결론입니다.** 같은 `inbox`에서 나간 둘이 다른 곳으로 갔고 그 판단 기준이 "증거인가 지식인가"였다는 것을 말하게 합니다.
- `SKILL.md`를 화면에 띄우고 쓰기 경계 문단을 함께 읽습니다.
- **에이전트가 묻는 자리에서 "응"만 하는 수강생이 반드시 나옵니다.** 그 자리에서 멈추고 정리본을 소리 내어 읽히십시오. 읽지 않은 승인은 승인이 아니고, 그러면 게이트를 둔 의미가 없습니다.
- **없는 슬러그로 게이트를 넘어 보라고 시킵니다.** `--related 아무거나1 --related 아무거나2`로 막히는 것을 직접 보게 하면 게이트가 무엇을 세는지가 남습니다.
- 에이전트마다 결과가 다릅니다. 정답을 맞추려 하지 말고 **왜 그 문서를 골랐는지 물어보게** 합니다.
- 스킬이 안 잡히면 에이전트를 재시작했는지 먼저 봅니다. 그다음 `engram skills install --dry-run`으로 경로를 확인합니다.
- `index.md`를 안 고치냐는 질문이 반드시 나옵니다. 고아 판정과 맞물린 자리이고 5단계 `backlinks`로 이어집니다.

|---|---|---|
| 표기를 갈랐습니다 | **터미널**, **에이전트에게**, 인용절 셋 | 4단계부터 두 주체가 섞입니다. 같은 모양으로 적으면 무엇을 쳐야 하는지 알 수 없습니다 |
| 에이전트를 4단계에서 붙입니다 | 7단계가 아니라 여기입니다 | 4단계가 처음으로 사람이 글을 써야 하는 자리입니다 |
| 거절을 먼저 겪습니다 | 정리 전에 그대로 `promote`해서 막힙니다 | 거절 경험이 교육이고, 에이전트를 왜 붙이는지가 그 자리에서 설명됩니다 |
| 정리는 에이전트가 합니다 | 사람이 본문을 쓰지 않습니다 | 원문을 읽고 정리하는 일이 이 도구가 없애려는 일입니다 |
| 이을 곳도 에이전트가 찾습니다 | `search`로 찾고 사람에게 묻지 않습니다 ([ADR 0052](../decisions/0052-agent-prepares-the-promotion-and-the-human-decides-it.md)) | 사람에게 묻는 것은 검색을 안 돌렸다는 뜻입니다 |
| 이을 곳은 이미 있는 문서입니다 | 없는 슬러그, 자기 자신, `inbox` 문서는 게이트가 안 셉니다 | 없는 슬러그 둘로 통과하면 게이트가 아무것도 막지 못합니다 |
| 사람이 하는 것은 둘입니다 | 원문을 지워도 되는가, 올릴 값어치가 있는가 | 커맨드를 붙여 넣는 것은 판단이 아닙니다. 승인은 커맨드가 아니라 문서 내용에 붙습니다 ([ADR 0057](../decisions/0057-approval-attaches-to-content-not-to-the-command.md)) |
| `promote`는 승인받고 에이전트가 칩니다 | 사람은 읽고 승인만 합니다 | 되돌릴 수 없는 `update`는 에이전트가 하는데 되돌릴 수 있는 `promote`를 사람에게 시키는 것은 거꾸로였습니다 |
| 제안 전에 `--dry-run`을 돌립니다 | 에이전트가 자기 제안을 스스로 검증합니다 | 게이트 통과 여부는 위키 상태를 계산해야 나옵니다. 짐작하면 틀립니다 ([ADR 0056](../decisions/0056-promote-has-a-dry-run.md)) |
| 순서가 있습니다 | 슬랙을 먼저, 원본 파생을 나중에 올립니다 | 게이트가 실재하는 대상만 세므로 걸 곳이 있는 쪽부터 올려야 합니다 ([ADR 0054](../decisions/0054-gate-counts-only-links-that-resolve.md)) |
| 세 자료가 세 길로 갑니다 | 기술문서는 `sources` 직행, 슬랙은 `context`, 전사는 `--to sources` | `inbox`의 탈출 경로가 셋이고 판단 기준은 증거인가 지식인가입니다 ([ADR 0058](../decisions/0058-promote-to-sources-moves-evidence.md)) |
| `index.md`는 자동 갱신하지 않습니다 | `backlinks index`로 대신 봅니다 | 색인이 전부를 가리키면 고아 판정이 영원히 0이 됩니다 |
| `mv`와 `archive`는 사람이 칩니다 | 에이전트에게 주지 않습니다 | 여러 파일을 한 번에 고치거나 단계를 옮깁니다 |
| 스킬은 전역 설치가 기본입니다 | 시험 중에는 `--dir`로 격리합니다 | 스킬 문서가 위키와 무관해서 하나면 되지만, 검증 중인 것이 모든 세션에 얹히면 안 됩니다 |
