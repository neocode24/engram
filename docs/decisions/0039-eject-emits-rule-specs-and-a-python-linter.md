# eject가 실제로 무엇을 내보내는가

## 배경

ADR [0013](0013-eject-redefined-seal-removed.md)이 `eject`를 "규칙의 소유권을 사용자에게 넘기는 행위"로 재정의하고 내보낼 것을 목록으로 적었다. `AGENTS.md`, `meta/` 규칙 문서, lint 스크립트, `.githooks/pre-commit`, `.gitattributes`다.

구현 착수 시점에 그 목록이 성립하지 않는다. **engram에는 그런 자산이 없다.** upstream에는 사람이 쓴 규칙 문서와 손으로 만든 `lint-frontmatter.sh`가 있지만, engram의 규칙은 Go 코드와 `engram.yaml`에만 있다. 내보내려면 **만들어 내야 한다.**

무엇을 어떤 형태로 만들어 낼지가 정해지지 않았다.

## 판단 근거

### 무엇이 소유권 이양인가

`engram.yaml`은 이미 사용자의 것이다. 축을 켜고 끄고, 허용값을 바꾸고, 임계값을 조정한다. 그런데도 eject가 필요한 이유가 있다면 그것은 **설정으로 표현할 수 없는 변경**이다. "게이트는 링크 두 개를 요구하되 `decision` 유형만 세 개" 같은 것이다.

그 변경이 가능하려면 **판정 논리가 사용자가 고칠 수 있는 파일에 있어야 한다.** 규칙 문서만 내보내고 판정은 engram이 계속하면 소유권이 넘어가지 않는다. 훅이 `engram lint`를 부르는 형태도 마찬가지다. 껍데기만 사용자 것이 된다.

**동등성 검증의 넷째 축이 이 판단을 뒷받침한다.** ADR [0005](0005-upstream-contract-and-harness.md)가 축 넷 중 넷째를 "`eject` 산출물과 upstream 스냅샷의 diff"로 적었다. 산출물이 upstream의 스크립트와 비교 가능한 종류여야 그 축이 성립한다.

### 어떤 언어인가

셋을 놓고 본다.

| 후보 | 문제 |
|---|---|
| bash | 프론트매터와 YAML 파싱이 취약하다. **upstream의 bash 린터가 실제로 CRLF 프론트매터를 인식하지 못한다.** 동등성 검증에서 측정한 사실이다 |
| Go | 사용자가 툴체인을 갖춰야 하고, 고치려면 다시 빌드해야 한다. 소유권 이양의 목적에 어긋난다 |
| **Python 표준 라이브러리** | 런타임 의존이 생긴다 |

**Python을 고른다.** 남는 문제는 런타임 의존 하나뿐이고 그것도 좁다. `pip`도 가상환경도 요구하지 않는다. YAML 파서를 쓰지 않고 프론트매터를 직접 파싱한다. 이 저장소의 `scripts/*.py`가 이미 같은 제약으로 돌고 있다.

ADR [0001](0001-purpose-and-scope.md)이 Python 설치 장벽을 문제로 들었으나 그 대상은 **첫 실습에 들어오는 수강생**이다. eject하는 사용자는 규칙을 직접 고치겠다고 결정한 사람이며 같은 부류가 아니다. 다만 Windows에서 Python이 기본 제공되지 않는다는 사실은 남으므로 안내에 적는다.

### 어디까지 내보내는가

ADR 0013이 축을 이미 그었다. **규칙 강제는 파일로 표현되고 연산은 안 된다.** 그 선을 그대로 쓴다.

| 종류 | 내보내나 |
|---|---|
| 문서 단위 규칙 판정. 프론트매터 스키마, 허용값, 링크 무결성, 승급 게이트 | 내보낸다 |
| 위키 단위 진단. `wiki.broad-topic` | 안 내보낸다 |
| 연산. 검색 색인, 재발견, 링크 그래프, 다이제스트 | 안 내보낸다 |

위키 단위 진단은 전체를 훑어 비율을 계산하는 일이라 문서 하나를 보는 훅의 자리가 아니다. 연산은 0013이 이미 제외했다.

### 내보낸 뒤에 검증한다

**내보낸 린터가 `engram lint`와 다르게 판정하면 eject는 사용자를 속인 것이다.** "이것이 당신을 막던 규칙입니다"라고 주면서 다른 규칙을 주는 셈이다.

그래서 골든 위키에 둘을 돌려 문서 단위 위반 목록이 같은지 본다. 동등성 검증이 upstream 스크립트를 상대로 하던 것을 자기 산출물을 상대로 하는 것이며, `harness/parity`의 대조 방식을 그대로 쓴다.

### 덮어쓰지 않는다

eject는 위키에 파일을 만든다. 이미 있는 파일을 말없이 덮으면 사용자가 고친 규칙이 사라진다. **eject는 단방향이라 되돌릴 수단이 없으므로**([0013](0013-eject-redefined-seal-removed.md)) 덮어쓰기가 곧 데이터 손실이다.

## 결정

**`eject`는 아래를 위키에 만든다. 전부 그 위키의 `engram.yaml`을 반영해 생성한다.**

| 산출물 | 내용 |
|---|---|
| `meta/*.md` | 규칙 명세 문서. 단계별 필수 필드, 허용값 집합, 임계값, 게이트 판정 |
| `scripts/lint-frontmatter.py` | 문서 단위 규칙을 판정하는 표준 라이브러리 Python 린터 |
| `.githooks/pre-commit` | 위 린터를 부른다 |
| `AGENTS.md` | 그 위키에서 일하는 에이전트의 작업 계약 |
| `.gitattributes` | 줄바꿈 처리 |

- **내보내는 범위는 문서 단위 규칙 판정까지다.** 위키 단위 진단과 연산은 engram에 남는다.
- 생성물은 `engram.yaml`을 읽는다. 값을 파일에 박지 않는다. 설정을 바꾸면 린터가 따라간다.
- **이미 있는 파일을 덮지 않는다.** 충돌하면 무엇이 충돌하는지 알리고 멈춘다. `--force`를 주면 덮되 무엇을 덮는지 먼저 낸다.
- `--dry-run`으로 무엇이 만들어질지 볼 수 있다. `sync`, `migrate`와 달리 기본값은 아니다. 파일을 새로 만드는 일이고 기존 문서를 고치지 않기 때문이다.
- **eject 이후에도 `search`, `recall`, `resurface`, `bridge`, `digest`, `backlinks`가 그대로 동작한다.** 0013의 핵심이며 출력에 그 사실을 적는다.
- 단방향이다. 되돌리는 커맨드를 만들지 않는다.

**내보낸 린터와 `engram lint`의 문서 단위 판정이 같아야 한다.** 골든 위키에서 대조하는 검증을 `harness/`에 둔다. 어긋나면 실패다. 이것은 측정이 아니라 계약이다.

## 결과

- 동등성 검증의 넷째 축이 성립한다. 축 넷 중 셋이 대조 대상을 갖게 된다.
- Windows에서 Python 없이 eject한 사용자는 훅이 안 돈다. `doctor`가 이 상태를 진단할 자리가 생긴다.
- 규칙 문서와 린터가 생성물이므로 engram의 규칙이 바뀌면 이미 eject한 위키와 어긋난다. 0013이 열린 항목으로 남긴 drift 문제이며 이 결정이 풀지 않는다. `doctor`가 경고하는 선까지가 그때의 방향이었다.
- `rules show`와 `eject`가 같은 내용을 두 형태로 낸다. 하나는 읽는 출력이고 하나는 도는 파일이다. 생성의 진실원을 하나로 두어야 둘이 어긋나지 않는다.
