# harness가 Pin 표면을 견본에 돌려 판정하고 화면만 바뀐 회차에만 화면을 가져온다

## 맥락

[0104](0104-upstream-pin-rules-are-held-out-of-the-harness.md)는 upstream의 `pin-rules.md`를 harness가 따라가지 않기로 했다. 따라갈 대상이 engram에 없었기 때문이다. [0106](0106-pin-ledger-is-declared-by-ingest-commands-and-written-on-loopback.md)이 그 대상을 만들었다. 위키 출처 하나만 옮긴 원장과 upstream의 화면 파일을 내장한 `/pin` 화면이다. 0106은 보류를 푸는 개정이 harness가 Pin 표면을 견주는 구현과 함께 들어가야 한다고 적고 그 결정을 이 문서로 미뤘다.

upstream의 Pin은 계약 파일 선언 밖에서도 바뀐다. 화면 파일(`scripts/pin/template.html`)은 닷새 동안 50번 바뀌었고, 그 가운데 10번은 상태의 형태를 늘렸다. 화면만 새것으로 바꾸고 상태 생성 코드를 옛것으로 두면 오류 없이 다른 내용이 보인다. 크롬으로 재현했을 때 10건 중 4건이 그랬다. 완료 집계 자리에 "아직 집계가 없습니다"가 나오거나 신호가 "주의"여야 할 자리에 "위험"이 나왔다. 화면, 상태 생성, 게이트는 한 벌로 움직여야 한다.

upstream의 `STATE_SCHEMA`와 CHANGELOG의 `impact`로는 이것을 가를 수 없다. 형태가 바뀐 10건 모두 `schema`가 1이었다. [0094](0094-engram-watches-its-own-dependency-surface.md)가 upstream의 표시를 읽지 않기로 한 이유와 같다. 파일 목록으로도 가를 수 없다. 생성 코드를 건드린 커밋 19건 가운데 9건은 출력이 같았고, 생성 코드를 건드리지 않은 커밋도 직전 커밋의 변경 때문에 형태가 바뀐 채 도착했다.

## 결정

**`scripts/upstream-sync.py`가 upstream 코드를 견본에 돌려 표면을 직접 견준다.** lock 커밋과 HEAD의 `scripts/pin`을 `git archive`로 꺼내 `harness/pin/fixtures` 견본(위키, 설정, 요청 묶음 다섯)에 같은 순서로 돌린다. upstream의 버전 표시는 읽지 않는다.

| 표면 | 어떻게 뜨나 |
|---|---|
| 화면 | 파일 해시 |
| 상태 형태 | 견본 원장에 상태 생성을 돌려 얻은 키 경로와 값의 형 집합 |
| 상태 값 | 같은 출력의 값 해시. 시각은 견본이 고정한다 |
| 게이트 | 요청 묶음마다 결과 코드, 사유 문장, 보관된 항목, 원장 파일 전체의 해시 |
| 상수 | 세 요청 경로의 허용 연산 표, 상태값, 대기 사유, 출처, 단계, 항목 키, 근거 키 |
| 화면 요청 | 화면 파일이 보내는 연산 이름 집합과 API 경로 집합 |
| 규칙 문서 | `pin-rules.md`에서 engram이 기대는 절의 본문 |

**판정은 셋이고 마지막 줄에 고정 문자열로 낸다.** `pin 판정: 유지`, `pin 판정: 화면만`, `pin 판정: PR`. 주간 잡은 이 줄을 읽는다. 화면 외 표면이 하나도 안 바뀌고 화면도 같으면 유지다. 화면만 바뀌면 화면만이다. 화면 외 표면이 하나라도 바뀌었거나 견본에 돌지 못한 표면이 있으면 PR이다. 표면마다 `유지 pin <표면>`, `갱신 pin <표면>` 줄이 먼저 나오므로 잡이 무엇이 바뀌었는지 읽을 수 있다.

**화면을 가져올지는 스크립트가 정한다.** 화면만 판정이 났을 때만 가져온다. PR 판정에서는 화면을 가져오지 않고 lock 시점 화면을 그대로 둔다. 잡 지시문에 "형태가 바뀌면 가져오지 마라"를 적는 방식은 쓰지 않는다. 0104가 적었듯 지시문이 지켜졌는지 확인할 길이 없다. PR 브랜치에서 사람이나 에이전트가 Go 구현을 고친 뒤에는 `--pull-page`로 판정과 무관하게 가져올 수 있다.

**가져올 때는 변환이 둘이다.** 설정 구역(`// pin:config begin`과 `end` 사이)의 값 한 줄을 engram 값(`API='/pin/api/'`, `SOURCES=['wiki']`, `AUTH='none'`)으로 바꾸고, 사이트 구역(`<!-- pin:site begin -->`부터 `end`까지)을 지운다. 표시 네 개가 정확히 한 번씩 없거나 값 한 줄이 정확히 한 번 맞지 않으면 가져오지 않고 실패한다(종료 코드 1, lock 변경 없음). 가져온 뒤에는 경계 검사를 돌리고, 가져온 화면이 걸리면 이전 화면으로 되돌리고 실패한다. 입력 예시 문구 같은 그 밖의 글은 바꾸지 않는다. upstream이 실명을 넣으면 경계 검사가 잡고 upstream에서 고친다.

**`pin-rules.md`의 보류를 푼다.** `HELD`가 비는 것이 이 결정의 코드 쪽 변경이다. 푼 뒤에도 파일 전체를 가져오지 않고 engram이 기대는 절만 `harness/upstream/pin-rules.md`에 둔다. 위키 문서에서 할 일을 찾을 때, 직접 입력과 원장 쓰기, 항목과 관계와 제안, 삭제의 첫 문단이다. 미리알림과 Hermes 절, 확인 표시 절이 바뀐 주는 `유지`다. 기대하는 절이 없으면 빈 사본을 만들지 않고 실패한다. 용어 사전을 표 형식 지문만 뜨는 선례와 같다.

**`pin/prompts/items.md`는 계약 밖 규범 문서로 [spec-map](../spec-map.md) 4.9절에 한 줄 더한다.** 에이전트가 일을 찾는 지시이고 upstream의 CHANGELOG 규율 대상이 아니라 바뀌어도 통보되지 않는다.

**회차별 처리.** 화면만 판정은 `main`에 바로 커밋한다. [0095](0095-hermes-is-the-harness-agent-and-the-pr-is-the-approval-point.md)가 파일이 전부 `유지`인 회차를 판단이 없다고 보아 직접 커밋하게 한 것과 같은 논리다. PR 판정은 화면, Go 구현, 견본 기대값을 한 PR에 담고 머지는 사람이 한다. 합격 기준은 `harness/pin`의 견주는 시험이 HEAD 기준으로 통과하는 것이다.

## 근거

**표면을 직접 돌리면 upstream의 약속에 기대지 않는다.** 위 실측대로 버전 표시도 파일 목록도 틀린다. 출력이 달라졌는지만 본다.

**화면, 상태 생성, 게이트가 한 벌이어야 한다.** 가져온 화면이 옛 상태 생성 위에서 오류 없이 다른 내용을 보이는 것이 가장 나쁜 실패다. 화면 외 표면이 하나라도 다르면 화면을 가져오지 않으므로 이 실패가 생기지 않는다. 뒤처져도 깨지지 않는다. 화면, 상태 생성, 게이트가 모두 lock 시점의 한 벌로 바이너리에 들어 있다.

**설정 구역 치환은 단순해야 한다.** 변환을 둘로 줄이고 표시가 하나라도 어긋나면 실패하게 해야 upstream이 화면 구조를 바꿨을 때 조용히 틀린 파일이 들어오지 않는다.

## 결과

- upstream이 빠르게 바뀌는 동안은 거의 매주 PR 판정이다. 지난 닷새를 커밋 단위로 보면 화면 외 표면이 바뀐 것이 적어도 11건이고, 주 단위로 묶으면 통째로 PR 한 건이다. 이 결정이 보장하는 것은 화면 변경이 자동으로 따라온다는 것이 아니라 따라가지 못한 주에도 Pin이 깨지지 않고 따라갈 때는 기계가 합격을 판정한다는 것이다.
- 견본이 지나지 않는 가지(예: 완료 뒤 보관 가운데 일부, 상위와 하위)에서만 생기는 키는 형태 지문이 놓친다. 견본을 늘리는 것이 대응이다.
- 견본은 위키 출처뿐이라 미리알림이나 Hermes에만 닿는 변경은 걸리지 않는다. 그것이 engram이 기대는 표면이다.
- upstream이 비공개라 CI는 견주는 시험을 건너뛴다([0029](0029-upstream-vendoring-and-parity-execution.md)와 같다). 판정 규칙 시험(`harness/pin/judge_test.go`)은 가짜 upstream을 임시 저장소로 만들어 돌므로 CI에서도 돈다.
- 주간 잡 지시문에 화면만 유형을 더하는 일은 이 결정 밖이다.
