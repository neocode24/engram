# Windows 콘솔의 한국어 출력

## 배경

Windows 실환경 검증에서 드러났다. 레거시 `cmd.exe`의 기본 코드페이지는 949이고, 그 콘솔에서 engram의 한국어 출력이 전부 깨진다.

```
?꾪솴
  inbox 1, source 0, context 0, archive 0 臾몄꽌
  ?꾪궎留곹겕 0媛? 怨좎븘 臾몄꽌 1媛?
```

Go는 문자열을 UTF-8 바이트로 쓰고, 코드페이지 949 콘솔은 그 바이트를 EUC-KR로 해석한다. 도구가 한국어로 말하는데 사용자가 읽을 수 없다.

CI는 이것을 잡지 못한다. 러너는 stdout이 파이프로 연결되어 콘솔 코드페이지가 개입하지 않는다. `windows-latest`와 `windows-11-arm` 양쪽에서 `go test`가 전부 통과했는데도 실제 콘솔에서는 읽을 수 없는 상태였다.

`windows/amd64`는 tier 1 플랫폼이다(ADR 0007). 교육 대상 다수가 Windows만 사용한다는 전제로 그렇게 정했다. 그 사용자들이 출력을 읽을 수 없으면 플랫폼 지원이라 할 수 없다.

## 판단 근거

**`doctor`의 경고로는 부족하다.** 현재 `doctor`가 코드페이지 949를 감지해 `chcp 65001`을 안내한다. 진단으로는 정확하다. 그러나 첫 실행에서 깨진 글자를 본 사용자는 `doctor`를 돌려 볼 생각을 하지 않는다. 깨진 화면 자체가 이미 이탈 사유다. 진단은 문제를 이해한 사람을 돕지, 문제를 처음 만난 사람을 돕지 못한다.

**출력 인코딩을 변환하는 방식은 기각한다.** UTF-8을 CP949로 바꿔 쓰면 콘솔 설정을 건드리지 않는다. 그러나 변환 테이블이 필요해 의존성이 붙고, CP949에 없는 문자는 손실된다. 무엇보다 출력 경로마다 변환을 통과시켜야 해서 한 곳이라도 빠지면 그 자리만 깨진다.

**콘솔 코드페이지를 바꾸는 것이 정공법이다.** Windows 콘솔 API `SetConsoleOutputCP(65001)`를 프로그램 시작 시 호출하면 그 뒤의 모든 출력이 UTF-8로 해석된다. 출력 경로를 하나도 고치지 않아도 된다.

**의존성 없이 가능하다.** 표준 `syscall` 패키지의 `NewLazyDLL("kernel32.dll")`로 kernel32 함수를 부를 수 있다. `golang.org/x/sys/windows`가 필요하지 않으므로 ADR 0007의 순수 Go 제약과 의존성 최소화 방침을 둘 다 지킨다.

**콘솔이 아닐 때는 건드리지 않는다.** stdout이 파이프나 파일이면 코드페이지가 개입하지 않는다. 그 상황에서 API를 부르면 실패하거나 무관한 콘솔을 바꾼다. 콘솔일 때만 적용한다.

**원래 코드페이지로 복원한다.** 프로그램이 사용자 콘솔의 상태를 영구히 바꾸는 것은 무례하다. 종료 시 복원하고, 복원 실패는 무시한다. 이미 출력이 끝난 뒤이므로 복원 실패가 결과를 바꾸지 않는다.

## 결정

**Windows에서 stdout이 콘솔이면 프로그램 시작 시 출력 코드페이지를 65001로 바꾸고, 종료 시 원래 값으로 되돌린다.**

- 구현은 `//go:build windows` 파일에 둔다. 다른 플랫폼은 아무것도 하지 않는 함수다.
- 표준 `syscall`만 쓴다. 새 의존성을 넣지 않는다.
- stdout이 콘솔이 아니면 아무것도 하지 않는다.
- API 호출 실패는 무시한다. 출력이 깨지는 것이 최악이지 프로그램이 죽는 것보다는 낫다.

`doctor`의 `env.console-encoding` 점검은 유지한다. 이 조치로 대부분 해결되지만, 리다이렉트된 출력을 다른 도구가 읽는 경우나 조치가 실패한 경우를 진단할 수단이 필요하다.

## 결과

- 레거시 `cmd.exe`에서 한국어 출력이 읽힌다. tier 1 플랫폼의 사용자가 첫 화면에서 이탈하지 않는다.
- 출력 경로를 고치지 않으므로 앞으로 추가되는 커맨드가 이 문제를 다시 만들지 않는다.
- CI가 이 회귀를 잡지 못한다. stdout이 파이프이기 때문이다. Windows 실환경 검증 절차에 이 항목이 남는다.
