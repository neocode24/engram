# 저장, 인덱스, 한국어 검색

## 배경

ADR 0007은 코어를 순수 Go, `CGO_ENABLED=0`으로 고정했다. 시맨틱 검색은 선택적 사이드카이며 실패 시 키워드 전용으로 강등된다. 즉 **키워드 검색이 이 제품의 기본 검색이자 최저 보장선**이다. 사이드카가 없어도, 사내망에서 모델 다운로드가 막혀도, 이 경로만은 반드시 동작해야 한다.

문제는 대상 문서가 한국어라는 점이다. 영어 기반 검색 엔진의 기본 토크나이저는 공백으로 자르는데, 한국어는 조사가 붙어 "위키에서", "위키를", "위키가"가 모두 다른 토큰이 된다. "위키"로 검색해도 아무것도 걸리지 않는다. 형태소 분석기는 사전을 요구하고, 쓸 만한 한국어 형태소 분석기는 대부분 Java나 C++ 구현이라 순수 Go 제약과 충돌한다.

또한 마크다운 파일 자체가 진실원인 상황에서 인덱스를 어디에 어떻게 둘지도 정해지지 않았다.

## 판단 근거

**진실원은 마크다운이어야 한다.** 이 제품의 전제는 사용자가 자기 파일을 소유한다는 것이다. ADR 0006의 `eject`가 성립하려면, 그리고 여정 13(git 동기화)이 성립하려면 데이터베이스가 진실원이 되어서는 안 된다. 인덱스는 언제든 버리고 다시 만들 수 있는 파생물이어야 한다.

**그러나 매번 전체 스캔은 답이 아니다.** upstream llm-wiki의 현재 규모는 마크다운 358개, 2.2MB다(2026-08-15 실측, `.git`과 로컬 캐시 제외). 이 정도는 전체 스캔으로도 견디지만, 재발견 루프(여정 9, 10, 11)는 문서 간 유사도와 링크 그래프를 반복 조회하고, 여정 22(검색 실패에서 재발견으로)는 실패한 검색어에 대해 추가 탐색을 건다. 매 호출마다 2.2MB를 파싱하고 그래프를 재구성하는 것은 대화형 응답 속도를 무너뜨린다.

**한국어 토크나이징에서 사전 내장은 제약과 충돌한다.** 형태소 사전을 바이너리에 넣으면 크기가 수십 MB 단위로 붇고, 미등록어(신조어, 사내 용어, 제품명)에 취약하다. 이 제품이 다루는 문서에는 미등록어가 특히 많다. 반면 문자 n-gram은 사전이 필요 없고 순수 Go로 구현되며 미등록어에 강하다. "위키에서"를 bigram으로 자르면 `위키`, `키에`, `에서`가 나오고, 질의 "위키"의 bigram `위키`와 일치한다. 조사 문제가 사전 없이 해소된다.

**n-gram의 비용은 품질이 아니라 인덱스 크기다.** 이 점을 분명히 해둔다. bigram 색인은 문서 길이에 거의 비례하는 수의 포스팅을 만들어, 원문 대비 인덱스가 수 배로 커진다. 2.2MB 규모에서는 무시할 수 있으나 수천 문서 규모에서는 재검토가 필요하다. 다만 이 제품의 대상은 개인과 소규모 팀의 지식 위키이고, 그 규모에서 인덱스 크기가 병목이 될 시점은 멀다. 지금 실측 없이 결정하되, 재검토 조건을 명시하는 편이 합리적이다.

**정밀도 저하는 검색 대상 축소로 보완된다.** bigram은 우연한 부분 일치로 오탐을 낸다. 그러나 이 제품의 검색 대상은 웹 전체가 아니라 사용자가 직접 쌓은 수백 개 문서다. 후보가 적으면 오탐의 절대량도 적고, 프론트매터의 축(`type`, `tags`, `artifact_stage`)으로 사전 필터링이 가능하다. 범용 검색 엔진이 감당해야 할 정밀도 요구를 이 제품은 지지 않는다.

## 결정

### 저장 구조

마크다운 파일이 진실원이다. 인덱스는 파생 캐시이며 언제든 삭제하고 재생성할 수 있다.

캐시 위치는 위키 루트의 `.engram/` 아래에 둔다. 사용자 전역 디렉토리가 아니라 위키 옆에 두는 이유는, 위키를 통째로 옮기거나 복사했을 때 캐시가 따라오지 않아 생기는 혼란을 막기 위해서다. `.engram/`은 `init`이 생성하는 `.gitignore`에 포함하여 커밋되지 않게 한다. 여정 13(2대 PC 동기화)에서 인덱스가 git 충돌을 일으키면 안 된다.

무효화는 파일 경로별 `mtime`과 크기 비교로 판정한다. 해시는 정확하지만 전체 파일을 읽어야 하므로 무효화 검사 자체가 전체 스캔이 된다. `mtime`이 어긋나는 환경(일부 동기화 도구, 체크아웃 직후)을 위해 `reindex --force`를 제공한다.

`doctor`가 인덱스 신선도를 점검 항목에 포함한다.

### 인덱스 구현

순수 Go로 직접 구현한다. 외부 검색 라이브러리를 쓰지 않는다.

근거는 두 가지다. 첫째, 기존 Go 검색 라이브러리는 대부분 영어 분석기를 전제하며 한국어 n-gram 토크나이저를 붙이려면 어차피 내부를 건드려야 한다. 둘째, ADR 0005의 conformance 테스트가 upstream 스크립트와의 출력 일치를 요구하는데, 외부 라이브러리의 랭킹 세부 구현이 바뀌면 그 일치가 깨진다. 랭킹을 우리가 소유해야 parity를 보증할 수 있다.

랭킹은 BM25를 쓴다. 파라미터 `k1`과 `b`는 설정으로 노출하지 않는다. 사용자가 조정할 수 있는 값이 아니며, 노출하면 지원 부담만 는다.

### 한국어 토크나이징

**문자 bigram 색인을 채택한다.** 형태소 사전을 내장하지 않는다.

세부 규칙은 아래로 한다.

- 한글 연속 구간은 bigram으로 자른다. 1글자 구간은 그대로 토큰으로 둔다.
- 라틴 문자와 숫자 구간은 공백과 구두점으로 자르는 통상 방식을 쓴다. `engram`, `min_wikilinks` 같은 식별자가 bigram으로 쪼개지면 검색이 망가진다.
- 한글과 라틴이 섞인 경우 문자 종류가 바뀌는 지점에서 먼저 분할한 뒤 각 구간에 위 규칙을 적용한다.
- 질의도 같은 토크나이저를 통과시킨다. 색인과 질의의 토크나이저가 다르면 일치가 성립하지 않는다.

토크나이저는 `internal/` 안에서 인터페이스로 분리한다. 훗날 사전 기반으로 교체하거나 선택 가능하게 만들 때 색인 구조 전체를 다시 쓰지 않기 위해서다.

### 시맨틱 검색과의 관계

ADR 0007이 정한 대로 시맨틱은 선택적 층이다. 키워드 결과와 시맨틱 결과를 합치는 방식은 이 ADR의 범위 밖이며, 시맨틱 사이드카를 실제로 붙이는 시점에 정한다. 다만 키워드 경로가 단독으로 완결되어야 한다는 제약은 여기서 확정한다. 시맨틱을 전제한 랭킹 설계를 하지 않는다.

## 결과

- 마일스톤 0.2의 검색이 외부 의존 없이 착수 가능해진다.
- `reindex` 커맨드의 존재 이유와 `--force` 플래그가 정해진다.
- `doctor` 점검 항목에 인덱스 신선도가 추가된다.
- `init`이 생성하는 `.gitignore`에 `.engram/`이 포함된다.
- 랭킹을 자체 구현하므로 ADR 0005의 parity 비교 항목에 검색 결과 순위를 넣을 수 있다.

## 열린 항목

- **인덱스 크기 재검토 조건.** 문서 수 2000개 또는 인덱스가 원문 대비 5배를 넘는 시점에 실측하고 재검토한다. 대안은 bigram 대신 가변 길이 n-gram, 포스팅 압축, 고빈도 bigram 가지치기다. 현재 upstream 규모(358개)는 이 조건에서 멀다.
- 시맨틱 결과와 키워드 결과의 결합 방식.
- 링크 그래프를 검색 인덱스와 같은 캐시에 둘지 분리할지. 여정 10과 11이 그래프를 반복 조회하므로 성능 측정 후 정한다.
