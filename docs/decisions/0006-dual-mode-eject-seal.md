# 0006 듀얼 모드와 모드 전환 커맨드

## 결정

바이너리는 두 가지 운영 모드를 지원한다.

- **easy mode**: 바이너리가 규칙을 내장한 채 전부 처리한다. 위키 폴더와 설정 파일만 있으면 되고, 게이트는 바이너리 내부 검증으로 강제된다.
- **hard mode**: upstream 위키의 원본 구조다. `AGENTS.md`와 스크립트 모음, git hook, lint가 실제 파일로 존재하고, 게이트는 pre-commit hook과 에이전트 계약으로 강제된다.

둘은 별개 제품이 아니라 하나의 성장 경로이며, 전환 커맨드가 연결 고리다.

| 명령 | 동작 | 비고 |
|---|---|---|
| `engram eject` | 내장 규칙을 실제 파일로 풀어놓는다. easy에서 hard로 | 확인 프롬프트, drift 경고 |
| `engram seal` | 풀어놓은 파일을 거두고 내장 규칙으로 복귀 | 파괴적. 로컬 수정분 diff를 먼저 보여준다 |
| `engram attach` | 이미 hard 구조인 위키에 바이너리를 붙인다 | 파일 변경 없음. 후순위 |
| `engram pack` | 배포와 공유용 번들 생성 | 예약어. 여정 14, 15에서 사용 |

## 근거

교육 대상은 두 층으로 갈린다. 대다수는 규칙의 내부 구현을 볼 이유가 없고 설치 한 방으로 바로 쓰기를 원한다. 소수는 규칙 자체를 자기 환경에 맞게 고치려 한다. 한쪽만 지원하면 나머지를 잃는다.

easy만 제공하면 도구가 블랙박스가 되어 "왜 이 문서가 승급을 거부당했는가"를 설명할 수 없다. hard만 제공하면 첫날이 환경 공사가 된다. `eject`는 이 둘을 순서로 만든다. 커리큘럼에서 1주차부터 4주차까지는 easy로 진행하고, 마지막 주차에 `eject`하여 그동안 자신을 막아 온 강제력의 실체를 파일로 열어 보인다. 도구 학습이 아니라 체계 학습으로 착지한다.

### 커맨드 이름 선택

`pack`을 모드 전환에 쓰지 않은 이유는 배포 번들 자리에 그 이름이 필요하기 때문이다. `export`와 `import`도 같은 이유로 기각했다. 반출(여정 14)과 외부 자료 수집(여정 3)이 그 이름을 먼저 차지한다. 초기 후보였던 `absorb`는 `seal`로 대체했다. `eject`의 반대 동작임이 이름에서 드러나야 하기 때문이다.

## ADR 0002와의 관계

0002는 "본인은 바이너리를 거의 사용하지 않는다"를 전제로 운영과 산출물을 분리했다. 이 결정은 그 전제를 바꾼다. 본인은 `eject`된 hard mode 사용자가 되며, 따라서 산출물 도구의 사용자 집합 안에 들어온다.

0002의 **결론(운영 도구와 산출물 도구의 분리, upstream이 진실원)은 유지**하고 근거만 갱신한다. 분리의 이유는 이제 "본인이 안 쓰기 때문"이 아니라 "같은 체계를 두 가지 강제 방식으로 제공하기 때문"이다. 0002는 `accepted`를 유지한다. 소급 수정 금지 원칙에 따라 0002 본문은 건드리지 않는다.

부수효과로 0002의 열린 긴장("본인이 안 쓰는 도구를 가르친다")이 해소된다.

## 열린 항목

- `eject`를 단방향으로 못 박을지 여부. 작성자 의견은 단방향으로 두고 `doctor`가 drift를 알리는 쪽이다. `seal`이 파괴적이라 왕복을 권장 경로로 만들면 사용자 데이터 손실 사고가 반복될 위험이 크다.
- `attach`가 인식해야 하는 hard 구조의 최소 조건. upstream 구조 전체를 요구할지, `meta/` 존재만으로 충분할지 미정.
