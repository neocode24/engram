# 0015 ADR 상태 어휘와 개정 색인

## 문제

ADR 0009부터 0014까지가 초기 결정 여럿을 실질적으로 바꿨다. 그런데 저장소 계약은 기존 ADR 본문의 소급 수정을 금지하고 frontmatter를 `number`, `title`, `date`, `status` 네 키로 제한한다. 그 결과 지금 문서를 처음 읽는 사람은 열네 건이 전부 `accepted`로 보이는 목록을 만나고, 그중 어느 절이 이미 뒤집혔는지 알 방법이 없다.

`amended_by` 같은 필드를 추가하면 개정이 일어날 때마다 **과거 ADR의 frontmatter를 고쳐야** 한다. 이는 소급 수정 금지의 취지를 형식적으로만 피해 가는 것이다. 개정 관계는 본질적으로 문서 사이의 관계이지 한 문서의 속성이 아니다.

## 결정

### 상태 어휘를 넷으로 고정한다

| 값 | 의미 |
|---|---|
| `accepted` | 유효하다. 본문 전체가 현재 결정이다 |
| `amended` | 결론은 유효하나 일부 절이 후속 ADR로 대체되었다 |
| `superseded` | 전체가 대체되었다. 이력으로만 읽는다 |
| `proposed` | 아직 확정 전이다 |

`deprecated`와 `rejected`는 두지 않는다. 채택되지 않은 안은 채택된 ADR의 "기각한 대안" 절에 근거와 함께 남기며, 별도 문서로 만들지 않는다.

### 개정 관계는 색인 파일에 둔다

`docs/decisions/README.md`가 전체 목록과 개정 그래프를 보유한다. 개정이 발생하면 색인에 한 행을 추가하고 대상 ADR의 `status`만 바꾼다. 본문은 건드리지 않는다.

`status` 변경을 소급 수정으로 보지 않는 이유는, 그 값이 결정의 내용이 아니라 결정의 **현재 유효성**을 가리키는 메타데이터이기 때문이다. 내용은 불변이고 유효성은 변한다.

## 적용

이 결정에 따라 아래 다섯 건의 상태를 조정한다.

| ADR | 변경 | 대체한 ADR과 대상 절 |
|---|---|---|
| 0003 | accepted에서 amended | 0013이 "웹 UI 포함 풀스펙 v1"을 마일스톤 분할로, 0014가 "에이전트 skill 내장"의 의미를 스킬 문서 배포로 확정 |
| 0004 | accepted에서 amended | 0012가 내부 미러를 배포 채널에서 격리 용도로 재정의 |
| 0006 | accepted에서 amended | 0013이 `seal`을 폐기하고 `eject`를 재정의, `attach`를 기본 동작으로 전환 |
| 0007 | accepted에서 amended | 0012가 winget과 scoop 우선 배포 절을 Homebrew tap 단일화로 대체 |
| 0002 | 변경 없음 | 0006이 근거만 갱신했고 결론은 유지된다. 0006 본문에 그 판단이 기록되어 있다 |

0001은 유지한다. Homebrew 배포 언급이 0007에서 후퇴했다가 0012에서 복권되어 결과적으로 원문과 일치한다.

## 결과

- 새 ADR을 쓸 때 과거 문서를 열어 볼 필요가 없다. 색인에 한 행만 추가한다.
- 개정 관계가 한곳에 모여 있어 "이 결정이 아직 유효한가"를 파일 하나로 답할 수 있다.
- `status`가 `amended`인 문서를 읽을 때는 색인에서 어느 절이 대체되었는지 먼저 확인해야 한다. 이 부담은 본문 소급 수정 금지의 대가이며 수용한다.
