# 제목과 본문이 같은 무게였다

## 배경

핸즈온 5단계를 검수하면서 `search`의 순위 근거를 설명하지 못한다는 것이 드러났다. 점수가 무엇인지 묻는 질문에 답이 없었고, 그 뒤에 더 큰 것이 있었다.

```go
func DefaultWeights() FieldWeights {
	return FieldWeights{Title: 1, Body: 1, Topics: 1, Tags: 1}
}
```

**`FieldWeights`는 처음부터 있었고 값은 전부 1.0이었다.** 주석이 "튜닝은 나중에 한다"고 적혀 있었으나 그 나중이 오지 않았다. 제목에 있는 낱말과 본문 스물세 번째 문단에 있는 낱말이 같은 무게였다.

[0010](0010-storage-index-and-korean-search.md)은 BM25와 bigram 토크나이저를 정했을 뿐 필드 가중치를 결정한 적이 없다. 값 넷은 결정이 아니라 미결이었다.

같은 검토에서 인접한 두 문제를 함께 봤고 둘 다 손대지 않기로 했다. 근거를 아래에 남긴다.

## 판단 근거

### 가중치

**필드마다 신호의 세기가 다르다.** 제목은 문서 전체가 무엇에 관한 것인지의 선언이고, `topics`와 `tags`는 스키마가 폐쇄 집합으로 관리하는 축이라 값이 붙었다는 것 자체가 사람의 분류 판단이다. 본문의 한 번 등장과 같은 무게로 두면 그 판단이 순위에 반영되지 않는다.

**값은 지어내지 않는다.** 같은 문제를 먼저 겪은 구현을 참고했다. SQLite FTS5 위에서 도는 개인 위키 검색 도구가 식별자 10, 제목 5, 본문 1을 쓰고 있다. 그 비율을 engram의 필드 구성에 옮긴다.

### 슬러그를 색인하지 않는다

참고한 구현은 식별자에 가장 큰 무게를 준다. engram에도 같은 것을 넣어 봤고 **두 가지 이유로 되돌렸다.**

**첫째, 중복이다.** engram의 기본 슬러그는 제목에서 파생된다(`SlugFromTitle`). 슬러그의 낱말은 이미 제목에 있으므로 따로 색인해도 같은 신호를 두 번 세는 것에 가깝다. 참고한 구현은 슬러그와 제목이 독립적으로 정해지는 구조라 사정이 다르다.

**둘째, `bridge`가 무너졌다.** 슬러그를 가중치 10으로 색인하자 `bridge`의 시험 셋이 실패했다. 원인은 명확하다.

```
후보가 없습니다
  context 문서 3개, 링크로 이어진 쌍 0, 기각된 쌍 0, min 0.30 미달 3
```

`bridge`는 색인의 TF 벡터로 문서 쌍의 코사인 유사도를 잰다. **슬러그 토큰은 문서마다 고유하다.** 서로 다른 두 문서가 공유할 수 없는 성분을 큰 무게로 벡터에 넣으면 유사도는 낮아지기만 한다. 슬러그 색인은 검색을 조금 돕고 재발견을 확실히 망친다.

**드러난 것은 색인 벡터에 소비자가 둘이라는 사실이다.** `search`는 문서를 지목하고 싶고 `bridge`는 내용의 닮음을 재고 싶다. 지금은 같은 벡터를 쓰므로 한쪽에 맞춘 가중치가 다른 쪽에 그대로 간다. 제목과 축은 두 소비자 모두에게 내용 신호이므로 충돌하지 않지만 슬러그는 아니다.

### 효과는 실데이터에서만 보였다

**문서 넷짜리 위키에서는 순위가 하나도 바뀌지 않았다.** 점수만 소수점 둘째 자리에서 움직였다. BM25가 TF를 문서 길이로 정규화하는데 `Length`가 가중치를 반영한 합이라, 제목 가중치를 올리면 분자와 분모가 함께 커지기 때문이다.

**실운영 위키 사본 308문서에서는 질의 일곱 중 다섯의 순위가 바뀌었다.** 판정할 수 있었던 질의에서 주제를 정면으로 다루는 문서가 위로 올라왔다.

이 대비 자체가 결과다. **가중치 변경은 문서가 쌓인 뒤에만 의미가 있고 픽스처로는 확인되지 않는다.**

### 손대지 않기로 한 둘

**접두 일치를 넣지 않는다.** 참고한 구현은 한국어 조사 문제를 질의어 뒤에 `*`를 붙이는 접두 일치로 푼다. engram은 bigram으로 이미 풀고 있다. 실측했다.

```
"게이트웨이는 프로토콜을 중계한다" 를 색인한 뒤
  질의 "게이트웨이" -> 토큰 [게이 이트 트웨 웨이], 누락 없음
  질의 "프로토콜"   -> 토큰 [프로 로토 토콜], 누락 없음
```

0010이 bigram을 고른 이유가 그대로 성립한다. 접두 일치로 바꾸면 색인이 작아지지만 색인 크기는 지금 문제가 아니다. 남는 차이는 라틴 구간에서 `config`가 `configuration`을 못 찾는 것 하나이며 열린 항목으로 남긴다.

**색인에 노출 필터를 넣지 않는다.** 민감도가 높은 문서가 검색에 걸린다는 지적을 확인했고 **결함이 아니었다.** `serve`는 `expose`가 판정한 집합으로 검색 결과를 걸러 내고 있으며([0044](0044-serve-is-read-only-and-shows-only-vetted-knowledge.md)), `export`는 같은 판정을 공유한다([0046](0046-pack-exports-files-and-anonymizes-by-user-dictionary.md), [0047](0047-export-not-pack.md)). 색인은 위키 전체를 담고 감추는 일은 소비자가 한다.

**이 분업을 색인 쪽으로 옮기면 안 된다.** 스킬 경로의 에이전트는 승급 준비를 위해 `sources`와 `inbox`를 검색해야 한다([0052](0052-agent-prepares-the-promotion-and-the-human-decides-it.md)). 색인에서 미리 걸러 내면 그 경로가 끊긴다. 색인 하나에 시야가 여럿인 구조가 옳다.

### 0010의 결과 항목 하나가 성립하지 않는다

0010은 결과에 이렇게 적었다.

> 랭킹을 자체 구현하므로 ADR 0005의 parity 비교 항목에 검색 결과 순위를 넣을 수 있다.

**upstream에 `search`에 해당하는 것이 없다.** 검색은 별도의 벡터 RAG에 위임되어 있고 비교할 스크립트가 없다. `docs/parity.md`의 비교 축은 `lint` 하나이며 둘째로 예정된 것은 `resurface`다. 검색 순위는 축이 될 수 없다.

**0010의 결정은 유지된다.** 자체 구현의 첫째 근거인 한국어 토크나이저는 그대로이고 [0007](0007-platform-and-distribution.md)의 `CGO_ENABLED=0`도 그대로다. 무너진 것은 둘째 근거 하나이므로 `status`를 바꾸지 않고 색인의 근거 갱신 표에 적는다.

이 정정이 없으면 가중치를 바꿀 때마다 parity가 깨진다고 오해하게 된다. **실제로는 가중치를 바꿔도 깨질 계약이 없다.**

## 결정

기본 가중치를 아래로 둔다. 본문을 1로 두고 나머지를 배수로 적는다.

| 필드 | 가중치 |
|---|---|
| 제목 | 5 |
| `topics` | 3 |
| `tags` | 3 |
| 본문 | 1 |

**제목의 실효 가중치는 6이다.** 제목은 본문의 첫 헤딩에서 뽑으므로 본문 색인에도 그대로 들어간다. 헤딩을 본문에서 걷어내지 않는다. 헤딩은 본문의 일부이며, 걷어내면 제목이 없는 문서와 있는 문서의 본문 정의가 달라진다. 시험을 짤 때 이 중복에 걸렸으므로 여기에 적어 둔다.

**슬러그는 필드가 아니다.** `FieldWeights`에 넣지 않는다.

가중치를 설정으로 노출하지 않는다. 0010이 `k1`과 `b`를 노출하지 않기로 한 것과 같은 이유다.

`SchemaVersion`을 2로 올린다. 가중치가 바뀌면 같은 문서의 TF 값이 달라지므로 1로 만든 색인은 낡은 것이다. `Load`가 버전이 다른 색인을 무시하므로 사용자는 아무것도 하지 않아도 되고 `search`가 이번 실행에서만 문서를 읽는다.

## 결과

- 제목과 분류 축의 일치가 순위에 반영된다.
- `.engram/index.json`이 한 번 무효화된다. `reindex`를 다시 돌리라는 안내가 나온다.
- `bridge`의 유사도는 바뀐다. 제목과 축의 무게가 늘었으므로 같은 주제의 문서 쌍이 서로 가까워지는 방향이다. 시험은 전부 통과한다.
- 시험 둘을 더했다. 질의어를 본문에 세 번 담은 문서보다 제목에 한 번 담은 문서가 위에 서는지, `topics`에 담은 문서가 본문에 담은 문서를 이기는지다. **변이 시험으로 검증했다.** 가중치를 전부 1.0으로 되돌리니 둘 다 실패한다. 색인 버전 판정 시험은 이미 있었다.

## 열린 항목

- **명시 슬러그가 제목과 다르면 그 낱말로 찾을 수 없다.** [0045](0045-explicit-slug-must-still-be-filesystem-safe.md)가 사용자의 명시를 존중하므로 실제로 어긋난 슬러그가 생길 수 있다. 요구가 나오면 슬러그를 제목과 합쳐 하나의 필드로 다루는 쪽을 먼저 본다. 별도 필드로 두면 `bridge`가 다시 무너진다.
- **라틴 구간에 접두 일치가 없다.** `config`가 `configuration`을 못 찾는다.
- **`캐시`와 `cache`는 다른 토큰이라 서로 걸리지 않는다.** 토큰 기반으로는 풀 수 없고 시맨틱 층의 몫이다.
- **색인 벡터의 소비자가 둘이라는 구조는 그대로 남는다.** 슬러그에서만 드러났을 뿐 원인은 해소되지 않았다. `bridge` 전용 벡터가 필요해지는 날이 오면 그때 나눈다.
