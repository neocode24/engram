# 슬러그는 파일시스템뿐 아니라 위키링크 문법에도 안전해야 한다

## 배경

[0045](0045-explicit-slug-must-still-be-filesystem-safe.md)가 명시 슬러그도 파일시스템 안전 검사를 받게 했다. 판정은 `unsafeFilenameRune` 하나가 하며 파생 경로는 문자를 지우고 명시 경로는 거절한다. 검사 대상은 Windows 예약 문자(`<>:"/\|?*`)와 제어 문자였다.

실습 자료를 쓰다가 다른 구멍이 드러났다. `capture`는 `--title`을 생략하면 본문 첫 줄에서 제목을 만든다. 회의 전사 파일의 첫 줄이 이랬다.

```
[자동 전사 결과. 화자 분리 정확도 낮음. 검수 안 됨]
```

만들어진 파일명이 `2026-08-17-[자동-전사-결과.-화자-분리-정확도-낮음.-검수-안-됨].md`가 되었다. 대괄호는 파일시스템에서 합법이므로 검사를 통과한다.

## 판단 근거

**대괄호가 든 슬러그는 본문에서 링크할 수 없다.** 실제로 확인했다. 그 문서를 가리키는 본문 위키링크를 쓰면 이렇게 된다.

```
[[2026-08-17-[개발-뉴스레터-발췌.-실습용-합성-자료]]]
```

여는 대괄호 둘과 닫는 대괄호 셋이라 짝이 어긋난다. 파서가 이것을 링크로 인식하지 않는다.

**그리고 아무도 알려주지 않는다.** 링크로 인식되지 않으므로 `link.broken`도 아니다. `backlinks`에 안 나오고 게이트의 링크 수에도 안 세어진다. `lint`가 `error 0`을 낸다. **조용히 사라지는 것이 이 결함의 핵심이다.** 깨진 링크는 알려주기라도 하는데 이것은 링크였던 적이 없는 것이 된다.

프론트매터의 `related` 필드는 YAML 문자열이라 영향을 받지 않는다. 그래서 같은 슬러그가 `related`로는 이어지고 본문으로는 안 이어지는 상태가 된다. 한 문서를 가리키는 두 경로가 다르게 동작하면 사용자가 원인을 찾을 수 없다.

**`#`도 같은 문제다.** 위키링크는 `[[슬러그#헤딩]]` 형태로 문서 안의 헤딩을 가리킨다. 슬러그에 `#`이 있으면 그 자리에서 잘린다.

**`|`는 이미 막혀 있다.** `[[슬러그|표시문자열]]`의 구분자인데 Windows 예약 문자라 파일시스템 검사에 이미 걸린다. 우연히 막힌 것이므로 근거를 여기에 적어 둔다.

**판정 함수를 나누지 않는다.** 0045가 "판정을 두 벌 두면 한쪽만 고치는 사고가 난다"고 적었다. 파일시스템 안전과 링크 문법 안전은 근거가 다르지만 결론이 같다. 슬러그에 쓸 수 없다는 것이다. 문자 집합을 둘로 나누어 근거를 구분하되 판정 함수는 하나로 둔다.

## 결정

`unsafeLinkChars`를 더한다. 값은 `[`, `]`, `#` 셋이다.

`unsafeFilenameRune`이 이 집합도 검사한다. 따라서 0045가 정한 두 경로의 동작이 그대로 적용된다.

| 경로 | 동작 |
|---|---|
| 파생 (`Slug`가 제목에서 만듦) | 문자를 지운다 |
| 명시 (`--slug`) | 거절하고 이유를 낸다 |

거절 메시지는 파일시스템 사유와 나눈다. 사용자가 `[`를 왜 못 쓰는지 알아야 하는데 "Windows에서 만들 수 없는 이름"이라고 하면 거짓이다.

```
슬러그에 위키링크 문법을 깨는 문자가 들어 있습니다: "메모[1]" (문제 문자: "[")
[]# 는 [[슬러그]] 표기와 겹쳐 본문 링크가 조용히 사라집니다. 빼고 다시 지정하세요
```

## 결과

- `capture`가 `--title` 없이 대괄호로 시작하는 줄을 만나도 쓸 수 있는 슬러그가 나온다. 위 전사 파일은 `2026-08-17-자동-전사-결과.-화자-분리-정확도-낮음.-검수-안-됨`이 된다.
- `--slug "메모[1]"`은 거절된다. 릴리스 전이라 밖에 그런 이름을 쓰는 위키가 없다.
- 회귀 시험 둘을 더했다. 파생이 지우는지와 명시가 거절하는지다. **변이 시험으로 검증했다.** 수정을 되돌리니 셋 다 실패했다.

## 열린 항목

- 마크다운 문법과 겹치는 다른 문자를 더 막을지. `*`와 `_`는 강조 표기이고 `` ` ``는 인라인 코드다. 다만 이들은 링크를 **깨지 않고** 표시만 바꾸며, 실제로 슬러그에 나타난 사례가 없다. 요구가 나오면 그때 본다.
- 슬러그의 마침표를 어떻게 볼지. `자동-전사-결과.-화자-분리`처럼 문장 부호가 그대로 남는다. 파일명으로 합법이고 링크도 깨지 않지만 보기 좋지 않다. 슬러그 정규화를 더 다듬는 것은 별개 결정이다.
