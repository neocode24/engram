# 노후 기준일 기본값을 30일로 한다

## 배경

`stale_days`는 `resurface`가 다시 꺼낼 문서를 고르는 기준이고 `status`의 밀린 문서 집계와 `digest`의 노후 집계도 같은 값을 읽는다. 기본값이 90이었다. upstream `scripts/wiki_resurface.py`의 `MIN_STALE_DAYS`는 30이다.

### 실측

실운영 위키 사본 308문서에 기본 설정으로 값만 바꿔 가며 쟀다. 기준 시각은 2026-08-19이고 `resurface`는 상한 없이 셌다.

| `stale_days` | `resurface` 후보 수 | `status`의 밀린 context 문서 수 |
|---|---|---|
| 30 | 55 | 55 |
| 60 | 30 | 30 |
| **90 (당시 기본값)** | **0** | **0** |

**기본 설정으로 재발견이 아무것도 내놓지 않는다.** 90일은 3개월 동안 한 번도 손대지 않은 문서만 꺼내겠다는 뜻인데, 살아 있는 위키에는 그런 문서가 없다. 재발견 루프 전체가 기본값에서 빈 화면을 내는 것은 기능이 없는 것과 같다.

### 90의 출처

찾지 못했다. [0009](0009-schema-presets-and-thresholds.md)가 네 임계값을 정한 ADR이며 게이트 임계값 표에 `stale_days` 90을 적었으나, 그 절이 근거를 붙인 값은 `min_wikilinks` 2 하나뿐이다("upstream 운영에서 나온 경험치"). 90에 대한 서술은 표의 숫자가 전부다. `docs/design.md`의 설정 표도 값만 옮겨 적었고, `stale_days`를 언급하는 나머지 ADR 둘([0028](0028-rediscovery-state-and-boundaries.md), [0066](0066-rediscovery-reads-inbound-links-and-ignores-bulk-commits.md))은 판정 절차만 다루고 값을 논하지 않는다. upstream 쪽 값은 30이므로 90은 upstream에서 온 값도 아니다.

## 판단 근거

**후보가 많은 것과 화면에 많이 나오는 것은 다르다.** 반대 논거는 30일이면 후보가 55건이라 재발견이 소음이 된다는 것이다. 그러나 `resurface`는 `--limit`으로 상한을 두고 기본값이 5다. 후보 55건 중 점수 상위 다섯만 화면에 나온다. 사용자가 더 보고 싶으면 상한을 올린다.

**반대로 후보가 0건이면 회복할 방법이 없다.** 상한은 후보 집합을 줄일 뿐 늘리지 못한다. 90에서 빈 결과를 받은 사용자가 할 수 있는 일은 설정 파일을 열어 임계값을 내리는 것뿐인데, 그러려면 먼저 이 값이 원인이라는 것을 알아야 한다. 두 오차의 비용이 대칭이 아니다.

**upstream 값과 맞는다.** 30은 upstream이 같은 성격의 위키를 몇 년 굴리며 쓴 값이다. 90에는 그런 근거가 없다.

### 측정 조건의 한계

사본이 git 저장소가 아니라 날짜를 프론트매터 값에서 그대로 읽었다. 실제 운영에서는 `sync`가 git 이력에서 `updated`를 채우므로 두 값이 다를 수 있다. 그 차이가 위 표를 뒤집을 만한지는 재지 않았다. 다만 [0066](0066-rediscovery-reads-inbound-links-and-ignores-bulk-commits.md)이 다룬 대량 커밋 문제는 git 이력 쪽 날짜를 **더 최근으로** 밀어 후보를 줄이는 방향이라, 기본값을 내리는 결정을 뒤집는 방향은 아니다.

## 결정

`stale_days` 기본값을 90에서 **30**으로 바꾼다.

값 하나만 바꾼다. 프리셋별로 다르게 두지 않는다. 임계값 넷이 프리셋과 무관하게 하나씩인 [0009](0009-schema-presets-and-thresholds.md)의 구조를 유지한다.

## 결과

- 기본 설정에서 `resurface`가 후보를 내놓는다. 사본 기준 55건이고 화면에는 `--limit` 기본값인 다섯이 나온다.
- `status`의 밀린 context 문서 수와 `digest`의 노후 집계도 같은 기준을 읽으므로 함께 바뀐다. 세 커맨드가 한 값을 공유하는 구조는 그대로다.
- `init`이 만드는 `engram.yaml` 템플릿, `README.md`의 설정 예시, `docs/design.md`의 임계값 표, `examples/personal`의 설정 파일이 모두 30이 된다.
- 이미 `stale_days`를 명시한 위키는 영향을 받지 않는다. 파일 값이 기본값을 덮는다.

## 열린 항목

- `bridge`의 유사도 하한 기본값 0.30은 바꾸지 않았다. 같은 실측에서 상위 다섯 쌍이 하한값과 무관하게 같았다. 정렬이 유사도 내림차순이라 하한을 내리면 상위가 아니라 꼬리만 길어진다. 0.30에서 256쌍이고 0.10까지 내리면 1418쌍인데 새로 들어오는 것은 전부 낮은 쌍이다. upstream `BRIDGE_MIN_SIM`은 0.18이지만 토크나이저가 달라 같은 척도가 아니므로 값을 그대로 옮길 근거가 없다.
- git 이력으로 채운 `updated`에서 다시 재면 후보 수가 얼마나 달라지는지는 미측정이다.
