# Hermes가 harness 에이전트이고 PR이 승인 지점이다

## 배경

[0094](0094-engram-watches-its-own-dependency-surface.md)가 upstream 변화를 engram 스스로 판정하게 만들었고, 그 판정을 주 1회 돌리는 Hermes 크론 잡을 붙였다. 잡은 `upstream-sync.py --check` 만 돌리고 아무것도 쓰지 않는다.

**감지까지만 만들고 반영은 안 만들었다.** 알림을 받은 사람이 그 뒤에 무엇을 어떤 순서로 하는지가 어디에도 없다. 실제로 밀린 18커밋을 맞출 때 사람이 매번 처음부터 절차를 다시 정했다.

[0029](0029-upstream-vendoring-and-parity-execution.md)가 "자동 반영하지 않는다. 사람이 판단해 시작하는 작업이다" 라고 적었다. 그 문장이 **판단**과 **작업**을 한 덩어리로 묶었다.

## 측정

### 밀린 것을 맞추는 일에 판단이 없었다

18커밋을 sync 했을 때 규칙 명세 일곱의 본문이 바이트 단위로 같았다. 사람이 한 일은 명령 한 줄이고 판단은 0이었다.

**이 경우가 흔하다.** upstream 은 위키이므로 문서 승급이 대부분이고 계약 파일은 드물게 바뀐다. 매주 사람을 부르면 부르는 쪽이 지친다.

### 판단이 필요한 경우는 따라 움직이는 것이 여럿이다

규칙 하나가 바뀌면 lint 규칙, `engram.yaml` 기본값, 골든 스냅샷, parity 기대값, 문서, ADR 이 함께 움직인다. 하나를 빠뜨리면 **모든 사용자가 쓰는 판정이 조용히 달라진다.**

그런데 그 작업의 대부분은 판단이 아니라 조사다. upstream diff 를 읽고, 무엇이 무엇으로 바뀌었는지 정리하고, engram 의 어디가 닿는지 짚는 일이다.

### 안전망이 이미 여럿이다

| 장치 | 무엇을 막나 |
|---|---|
| `check-boundary.py` (커밋 훅) | 사내 식별자가 공개 저장소로 나가는 것 |
| `check-adr.py` (커밋 훅, CI) | ADR 색인이 어긋난 채 커밋되는 것 |
| `harness/parity` | engram 판정이 upstream 스크립트와 갈리는 것 |
| 골든 스냅샷 | 판정이 바뀌었는데 diff 에 안 드러나는 것 |
| CI | 빌드, 시험, 교차 빌드, 전사 |

## 판단 근거

### 판단과 작업을 나눈다

[0029](0029-upstream-vendoring-and-parity-execution.md)가 지키려던 것은 **사람이 판단한다**이지 사람이 손으로 친다가 아니다. [0057](0057-approval-attaches-to-content-not-to-the-command.md)이 같은 것을 이미 정했다. 에이전트가 준비하고 사람은 내용을 보고 승인한다.

작업을 Hermes 에 맡기고 판단 지점을 PR 로 옮긴다. **PR 이 승인 지점이다.**

### 두 갈래를 다르게 다룬다

| | 규칙 명세가 그대로 | 규칙 명세가 바뀜 |
|---|---|---|
| 신호 | 파일별 전부 `유지` | `갱신` 이 하나라도 있음 |
| 판단 | 없음 | 있음 |
| Hermes | sync 하고 `main` 에 **직접 커밋하고 푸시** | 브랜치를 파고 **PR** |

갈래 A 를 PR 로 만들지 않는 이유가 있다. 볼 것이 없는 PR 이 매주 쌓이면 사람이 읽지 않고 머지하는 습관이 붙고, 그러면 갈래 B 의 PR 도 같이 넘어간다. **PR 이 오는 것 자체가 볼 것이 있다는 신호여야 한다.**

### 코드까지 고치게 한다

갈래 B 에서 Hermes 가 조사만 하고 코드를 안 고치는 안을 검토했다. 기각한다.

사람이 PR 을 보고 판단하는 것은 어느 쪽이든 같다. 그런데 코드가 없는 PR 은 **읽을 것이 산문뿐이라 판단이 추상적이다.** 실제 diff 가 있으면 무엇이 어떻게 달라지는지가 눈에 보이고, 골든 스냅샷 diff 가 판정 변화를 그대로 드러낸다.

틀린 코드를 막는 것은 사람이 코드를 쓰는 것이 아니라 PR 을 읽는 것이다.

### 자동 머지를 하지 않는다

이것 하나가 무너지면 위의 전부가 무의미하다. Hermes 는 PR 을 열기만 하고 머지하지 않는다.

**골든 스냅샷 재생성을 특별히 다룬다.** `-update` 를 주면 기대값이 현재 출력으로 덮인다. 그것으로 어떤 변경이든 초록으로 만들 수 있어 시험이 신호를 잃는다. Hermes 는 재생성해도 되지만 **PR 본문에 무엇이 어떻게 바뀌었는지 적어야 하고**, 사람은 그 diff 를 읽고 머지한다.

## 결정

| 항목 | 값 |
|---|---|
| 역할 | Hermes 주간 잡이 **harness 에이전트**다. 감지에서 반영 준비까지 한다 |
| 갈래 A (전부 `유지`) | sync 하고 `main` 에 직접 커밋하고 푸시한다. 판단이 없다 |
| 갈래 B (`갱신` 있음) | 브랜치를 파고 코드까지 고쳐 **PR 을 연다** |
| 승인 지점 | **PR 머지.** Hermes 는 머지하지 않는다 |
| 골든 재생성 | 해도 된다. 단 **PR 본문에 무엇이 바뀌었는지 적는다** |
| PR 에 반드시 담을 것 | upstream 의 무엇이 무엇으로 바뀌었나, engram 의 어디를 고쳤나, parity 결과, 골든 diff 요약 |
| 반영 절차 | [spec-map](../spec-map.md) 6절에 순서로 적는다 |

## 결과

- 밀린 lock 이 사람 손 없이 매주 맞춰진다. 그 전에는 엿새를 밀리고도 몰랐다.
- 규칙이 바뀌면 조사가 끝난 PR 이 온다. 사람은 판단만 한다.
- **PR 생성이 이 잡에 한해 허용된다.** `AGENTS.md` 의 "PR 생성은 명시적 승인이 필요하다" 에 예외가 생긴다. 이 ADR 이 그 승인이다.
- `main` 브랜치 보호가 없으므로 갈래 A 의 직접 푸시가 기술적으로 가능하다. 보호를 걸면 갈래 A 도 PR 이 되어야 한다.
- Hermes 가 잘못 고친 PR 을 사람이 머지하면 그대로 나간다. 이 구조의 유일한 실패 지점이다.
