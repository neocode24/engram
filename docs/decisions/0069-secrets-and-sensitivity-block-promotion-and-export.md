# 시크릿과 민감도가 승급과 반출을 막는다

## 배경

upstream 대조 감사에서 나온 구멍이 둘이다.

첫째, `docs/spec-map.md` 4.7절은 security-rules.md에 대해 "코드로 강제하는 것. **없다.**"라고 적었다. 시크릿이 위키에 들어오는 것과 민감 자료가 올라가는 것을 바이너리가 전부 사람에게 맡겼다.

둘째, [0063](0063-exposure-reads-indexable-status-and-scopes-internal.md)이 노출 판정에서 반출 쪽을 닫았다. `sensitivity: internal` 문서가 기본으로 나가던 길을 막았다. 그런데 승급 쪽은 그대로 열려 있었다. `internal/cli/promote.go`에 `sensitivity` 문자열이 하나도 없었다. 민감 자료가 `context`로 올라가는 것 자체를 아무도 막지 않았고, 올라간 문서는 `serve`와 `mcp`로 에이전트에게 나간다.

upstream은 시크릿을 pre-commit 훅에서 검사한다. engram의 위키는 git 아래 있지 않을 수도 있어 커밋 훅에 그 자리가 없다. 검사가 들어갈 자리는 커밋이 아니라 위키를 고치는 커맨드다.

## 판단 근거

### 패턴을 여섯으로 좁힌다

PEM 개인키 헤더, AWS 액세스 키 ID, GitHub 토큰, Slack 토큰, HTTP Authorization Bearer 헤더, 사용자 홈 경로 여섯이다.

오탐 한 건이 규칙 전체의 신뢰를 깎는다. 시크릿 검사가 맞는 것을 틀렸다고 알리면 사용자는 다음 거절부터 무시하고 우회법을 찾는다. 그래서 전부 실제 형식을 그대로 요구하는 패턴만 둔다. 엔트로피 기반 판정을 넣지 않는다. 문자열의 무작위성을 재는 판정은 짧은 위키 문서에서 흔한 슬러그, 해시, 합성어를 자주 잡는다.

패턴을 늘리는 것은 요구가 실제로 나올 때 한다. 늘릴 때마다 오탐 비용을 함께 재어 기존 여섯의 신뢰를 깎지 않는지 본다.

### 코드 펜스 안을 검사한다

위키링크 추출(internal/doc)은 코드 펜스를 건너뛴다. 링크 문법은 문서에 설명으로 등장하기 때문에 펜스 밖만 세어야 판정이 틀어지지 않는다. 시크릿은 반대다. 실제 시크릿은 코드 블록에 붙여 넣는 일이 더 흔하다. 그래서 펜스 안을 포함해 전문을 검사한다.

### --force를 두지 않는다

[0064](0064-update-refuses-to-change-sources.md)는 `update`에 `--force`를 뒀다. 원본 보존 계층을 고치는 것이 정당한 경우, 오타 정정이나 잘못 붙은 채널 값이 실재하기 때문이다.

이번에는 그런 경우가 없다. 시크릿이 든 문서를 그대로 `context`로 올리는 것이 정당한 경우는 없다. 우회가 필요하면 문서에서 시크릿을 지우면 되고 그 행위가 곧 기록으로 남는다. 민감도는 더 직접적인 우회로가 이미 있다. 문서의 `sensitivity` 값을 고치는 것이다. 값을 고치는 행위가 곧 사람의 판단이고 프론트매터에 남는다. `export` 쪽은 더 강하다. 파일이 기계 밖으로 나가는 행위이고 되돌릴 수 없다.

### 반대 논거: 교재와 예시 문서에 가짜 키를 쓰면 걸린다

이 도구는 교재와 예시 위키를 자기 산출물로 낸다. 강의 자료에 가짜 토큰을 보기로 심어 두면 그 위키를 검사하는 도구가 자기 산출물을 거절한다. 도구가 자기 산출물로 자기 검사를 통과해야 한다는 원칙과 부딪힌다.

이 논거를 진지하게 검토했다. 기각 근거는 여섯 패턴이 전부 실제 형식을 그대로 요구한다는 것이다. GitHub 토큰은 `ghp` 뒤 36자 이상, AWS 키는 `AKIA` 뒤 16자의 대문자와 숫자다. 설명용 예시가 그 형식을 흉내 낼 이유가 없다. 교재는 자리 표시자로 쓰면 되고 그것은 어느 패턴에도 걸리지 않는다. 홈 경로 패턴만 문서의 예시 경로와 실제 사용자의 홈 경로를 코드가 가를 수 없다는 문제가 있으나, 예외를 두면 그 예외로 실제 시크릿도 통과하게 되므로 두지 않는다.

실측으로 확인했다. 2026-08-19에 `engram lint --json`을 돌린 결과 `examples/personal`은 문서 7개에서 `security.secret` 0건, `harness/fixtures/golden-wiki`은 문서 16개에서 0건이다. 도구는 자기 산출물로 자기 검사를 통과한다.

### 막는 방향과 막지 않는 방향

- `--to sources`는 민감도로 막지 않는다. `sources`는 노출 판정에서 이미 닫혀 있다([0063](0063-exposure-reads-indexable-status-and-scopes-internal.md)).
- `demote`와 `archive`는 막지 않는다. 내려가는 방향이다.
- `sensitivity` 축이 꺼진 위키에서는 민감도를 판정하지 않는다.
- 시크릿은 `--to sources`도 막는다. 시크릿은 증거 계층에도 두면 안 된다. 민감도와 다른 점이다.
- `new`도 같은 진입점으로 검사받는다.

## 결정

판정 함수는 `internal/secret`의 `Scan` 하나다. 같은 판정을 두 벌 두면 어느 커맨드는 통과하고 어느 커맨드는 거절하는 문서가 생긴다. 세 커맨드와 `lint`가 이 하나를 부른다.

| 커맨드 | 민감도 | 시크릿 |
|---|---|---|
| `promote` (context) | `sensitivity` 축이 켜져 있고 값이 `restricted` 또는 `private-local-only`이면 거절 | 하나라도 걸리면 거절 |
| `promote --to sources` | 검사하지 않음 | 하나라도 걸리면 거절 |
| `new` | `promote`와 같은 진입점 | `promote`와 같은 진입점 |
| `export` | 노출 판정에 맡김 | 치환 뒤 본문에서 하나라도 걸리면 아무것도 쓰지 않고 거절 |
| `serve` | 검사하지 않음 | 검사하지 않음 |

거절 메시지는 규칙 이름과 줄 번호만 낸다. 값은 출력하지 않는다. 거절 메시지가 로그와 터미널 스크롤백으로 옮겨지면 그것 자체가 유출이다.

lint 규칙 `security.secret`을 `error` 등급으로 더한다.

## 결과

lint 규칙이 16종에서 17종이 된다. `docs/spec-map.md` 4.7절의 "코드로 강제하는 것. 없다"가 채워진다.

캡처 즉시 inbox 문서의 민감도 기본값은 `private-local-only`다. `sensitivity` 축이 켜진 위키에서 `promote`는 이제 사람이 값을 `public-reference`나 `internal`로 확정해야 통과한다. 값의 확정이 곧 승급 심사의 기록이 된다.

## 열린 항목

- `serve`는 검사하지 않는다. 로컬호스트에 묶여 있고 파일이 기계 밖으로 나가지 않기 때문이다. 노출 범위는 [0044](0044-serve-is-read-only-and-shows-only-vetted-knowledge.md)의 노출 판정이 이미 정한다.
- `home-path` 패턴은 오탐을 낼 수 있다. 홈 경로 형태의 예시를 문서에 적으면 걸린다. 지우거나 자리 표시자로 바꾸는 것이 해법이나, 실제 위키에서 걸리는 빈도가 문제가 되면 그때 다시 논의한다.
