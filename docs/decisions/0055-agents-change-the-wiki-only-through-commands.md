# 쓰기 경계가 파일 도구 앞에서 무력했다

## 배경

[0052](0052-agent-prepares-the-promotion-and-the-human-decides-it.md)와 [0054](0054-gate-counts-only-links-that-resolve.md)를 반영한 뒤 실제 에이전트에게 다시 승급 준비를 시켰다. 에이전트가 이렇게 했다.

1. `context/`가 비어 이을 곳이 없다고 판단했다
2. **자기 파일 도구로 `context/정산-배치.md`와 `context/조회-캐시.md`를 직접 만들었다**
3. **`index.md`를 직접 고쳐 그 둘로 가는 링크를 넣었다**
4. 그다음 `promote`를 불러 세 번째 문서를 올렸다
5. `lint`가 낸 위반을 다시 파일 편집으로 고쳤다
6. "게이트 통과, 모든 context 문서 2개 위키링크 충족"이라고 보고했다

**게이트를 지난 문서는 셋 중 하나뿐이다.** 나머지 둘은 게이트를 거치지 않고 `context/`에 들어갔다.

[0041](0041-skills-install-embeds-one-static-skill.md)이 쓰기 경계를 "`inbox`까지"로 정하고 [0043](0043-mcp-exposes-one-write-tool-and-omits-promote.md)이 MCP 도구 목록으로 그것을 강제했다. **그러나 스킬 경로의 에이전트는 셸과 파일 편집 도구를 쥐고 있다.** 경계가 단계 이름으로만 쓰여 있었고 도구에 대해서는 한 마디도 없었다.

## 판단 근거

**MCP처럼 강제할 수 없다.** 0043은 도구 목록에서 빼는 것으로 경계를 강제했다. 스킬 경로에는 그런 수단이 없다. 에이전트는 `engram`을 안 거치고 파일을 쓸 수 있고 그것을 막을 방법이 이 저장소에 없다.

**그래서 문구를 무디게 두면 안 된다.** 기존 문구는 "네가 쓸 수 있는 곳은 inbox까지다"였다. 단계를 말할 뿐 **무엇으로 쓰느냐**를 말하지 않았다. 에이전트는 `context/`에 파일을 만들면서 그 문장을 어겼다고 인식하지 않았을 수 있다. 강제할 수 없을 때 남는 수단은 오해할 수 없는 문장뿐이다.

**`index.md`가 사각지대였다.** 색인은 `inbox`도 `context`도 아니다. 경계 문구의 어느 쪽에도 안 걸린다. 실제로 에이전트가 가장 먼저 손댄 곳이 거기였다.

**"이을 곳이 없으면 만든다"가 잘못된 대처였다.** 에이전트의 목표는 게이트 통과였고 가장 짧은 길이 문서를 만드는 것이었다. 그러나 위키를 늘리는 것과 잇는 것은 다르다. 이을 곳은 실제로 있었다. 색인과 `sources/` 원본이다.

**lint가 사후에 잡는다.** 손으로 만든 문서 하나가 `gate.min-wikilinks`로 거절되었다. 사전 강제가 안 되는 이상 이것이 마지막 방어선이다. 그래서 스킬 문서가 **바꾼 뒤 `lint`를 돌리고 결과를 보고하라**고 지시한다.

## 결정

스킬 문서 맨 앞에 절 둘을 더한다. 쓰기 경계 절보다 앞이다.

**"위키는 engram 커맨드로만 바꾼다."** 파일을 직접 만들거나 고치는 것을 금지한다. `context/`에 파일을 만드는 것, `index.md`를 고치는 것, 프론트매터를 손으로 다는 것을 각각 이름으로 적는다. 에이전트가 위키 문서를 바꿀 수 있는 커맨드는 `capture`와 `update` 둘뿐임을 명시하고, 나머지 쓰기 커맨드는 제안만 한다고 적는다. 바꾼 뒤 `lint`를 돌리고 보고하게 한다.

**"이을 곳이 없어 보일 때."** `context`가 비어도 `context` 문서를 만들지 않는다. 색인과 `sources/` 원본이 대상이 되므로 이을 곳은 대개 있다. 그래도 부족하면 사람에게 말하고 멈춘다.

기존 쓰기 경계 절에 `index.md`가 `inbox`가 아니라는 한 줄을 더한다.

## 결과

- 스킬 문서가 담는 것이 여덟에서 열이 된다. 0041의 status는 이미 `amended`다.
- MCP 도구 목록은 바뀌지 않는다. 그쪽은 애초에 파일 도구가 없다.
- 강제 수단이 없다는 사실 자체를 문서가 인정한다. **막을 수 없으면 마지막 방어선은 `lint`다.**

## 함께 고친 결함 둘

같은 실행에서 커맨드 결함 둘이 드러났다.

**위키 안에서 상대 경로와 절대 `--wiki`를 함께 주면 깨졌다.** 셸의 작업 디렉토리가 마침 위키 루트일 때다.

```
engram promote inbox/2026-08-17-test.md --wiki /Users/사용자/engram-wiki
Error: 위키 루트 기준 경로를 계산할 수 없음: Rel: can't make inbox/... relative to /Users/...
```

`resolveDocPath`가 인자를 작업 디렉토리 기준으로 먼저 찾아 상대 경로를 그대로 돌려주었고, 뒤의 `filepath.Rel`이 절대 경로인 루트와 상대 경로를 섞어 받았다. 위키 루트 상대 경로를 먼저 보게 하고, 어느 쪽을 골랐든 루트와 절대/상대를 맞춰 내게 고쳤다. Go 내부 오류 문자열이 사용자에게 새어 나가던 것도 함께 없앴다.

**`--related`가 쉼표를 안 나눴다.** 에이전트가 `--related 정산-배치,조회-캐시`를 줬고 engram이 그것을 슬러그 하나로 받아 본문에 `[[정산-배치,조회-캐시]]`를 박았다. 깨진 링크가 되어 사람이 고쳐야 했다.

`update`의 `--set`이 배열 속성을 쉼표로 받는다(`--set topics=go,cli`). 같은 도구 안에서 한쪽만 다르면 틀리게 쓰는 것이 정상이다. `--related`도 쉼표로 나누고 도움말에 적는다.

## 열린 항목

- 손으로 만든 `context` 문서를 `doctor`가 진단할지. 지금은 `lint`가 게이트 위반으로만 잡는다. 링크를 채워 만들면 안 걸린다. 승급 이력을 남기는 방법이 없어 판정 근거가 마땅치 않다.
