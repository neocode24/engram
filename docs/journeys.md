# 사용자 여정

> 커맨드 체계와 마일스톤은 [design.md](design.md)에, 동작 구조는 [architecture.md](architecture.md)에 있다. 이 문서는 **사용자가 실제로 겪는 시나리오**를 다룬다.

여정은 24개다. 초판은 15개였고 정기 운영 동선만 촘촘했는데, 도구 생애주기 동선(설치, 모드 전환, 되돌리기, 업그레이드)이 통째로 비어 있어 9개를 추가했다. 뼈대는 upstream 위키의 워크플로 문서에서 가져왔다.

## Z. 도입과 생애주기

**0. 설치와 첫 위키**
설치, `init` 마법사, `doctor`, 첫 문서 작성까지. 커리큘럼 1단위의 실체이자 사내 배포에서 이탈이 가장 많이 나오는 구간이다. `init`은 대상 폴더, 스키마 프리셋, 언어, git 초기화, 시맨틱 검색 사용 여부를 순서대로 묻고 각 질문에 왜 묻는지 한 줄을 붙인다. 폴더를 만들면서 역할을 그 자리에 인쇄한다.

```
inbox/    처리 대기. 아무거나 던져 넣는 곳입니다. 여기 있는 건 지식이 아닙니다.
sources/  원본 보존. 한 번 들어오면 고치지 않습니다.
context/  검수된 지식. 여기 올리려면 게이트를 통과해야 합니다.
```

이 세 줄이 강의 1단위의 압축판이다.

**16. eject와 hard 전환**
커리큘럼 마지막 단위의 클라이맥스. 그동안 자신을 막아 온 강제력의 실체를 파일로 열어 본다. 도구 학습이 아니라 체계 학습으로 착지한다. eject 이후에도 검색과 재발견은 그대로 동작한다.

**17. 업그레이드와 사내망**
`self-update`, 프록시 경유, 오프라인 모델 번들. 폐쇄망에서 모델 다운로드가 막혔을 때 코어가 정상 동작하는지가 이 여정의 합격 기준이다.

## A. 입력

**1. 회의록**
회의 중 러프 캡처, 회의 후 구조화(결정, 액션, 미결), 액션 아이템을 외부 이슈 트래커와 캘린더로 반출, 다음 회의 직전 이전 회의록 자동 회수. **마지막 고리가 핵심 가치다.** 앞의 세 단계만 있으면 그냥 메모장이다.

**2. 음성 녹음**
전사, 화자 분리, 용어 사전 자동 치환, 사람이 오탈자 교정, 교정 내역이 사전에 피드백되어 다음 전사가 개선된다. 이 피드백 루프가 숨은 무기다. 원본 오디오는 커밋하지 않는다. 로컬 전사는 무거우므로 바이너리는 외부 전사기 호출과 결과 수용 인터페이스만 정의한다.

**3. 텍스트 드롭**
링크나 클립보드 내용을 한 번에 캡처한다. 마찰이 있으면 안 쓰게 되는 동선이다.

**4. 주간 뉴스 수집**
정기 수집, 요약, 관심사 필터. 요약은 에이전트가 한다.

## B. 승급

**5. inbox 정리 세션**
쌓인 inbox를 훑으며 폐기, 원본화, 승급으로 분류한다. 며칠째 몇 개가 쌓였는지 압력 지표가 필요하다. `status`가 이를 보여준다.

**6. 게이트 실패와 교정**
`promote`가 거절되고 무엇을 채워야 하는지 안내받아 통과한다. 대표 시나리오는 위키링크가 `min_wikilinks` 미만이라 거절되는 경우다. **거절 경험이 곧 교육이므로 에러 메시지 품질이 제품 품질이다.** "검증 실패"로 끝내면 안 되고 현재 값, 필요 값, 다음 명령을 함께 준다.

**18. context 직접 생성**
승급 경로가 아니라 처음부터 개념 노드를 `context/`에 직접 쓴다. `new`가 이 동선이며 `promote`와 같은 게이트를 지난다.

**19. 되돌리기**
잘못 승급한 문서를 `demote`로 강등하고, `migrate` 오적용을 복구한다. 게이트를 강제하는 제품일수록 되돌리기가 신뢰를 만든다. 여정 6은 거절만 다루고 오작동은 다루지 않는다.

**20. 폐기와 archive**
수명이 끝난 문서를 걷어낸다. 위키가 커질수록 이것이 주된 노동이 된다. `archive`에서 나가는 경로는 자동으로 열리지 않으며 되살리려면 사람이 명시적으로 다시 승급한다.

## C. 회수

**7. 작업 중 회수**
현재 작업과 관련된 과거 지식을 검색으로 꺼낸다. 사람이 직접 찾는 경우와 에이전트가 대신 꺼내오는 경우를 모두 포함한다.

**8. MCP 연결**
위키를 MCP 서버로 노출한다. 쟁점은 쓰기 권한 범위다. 에이전트가 `context`에 직접 쓰면 승급 게이트 철학이 무너지므로 **MCP 쓰기는 inbox까지만 허용하고 승급은 사람 확인을 강제한다.** 이것이 다른 PKM MCP와의 차별점이 된다.

**21. 판단 기준 회수**
외부 문서를 검토할 때 위키에 쌓인 체크리스트와 판정 절차를 꺼내 적용한다. 위키가 쌓는 곳만이 아니라 꺼내 쓰는 곳이라는 동선이며 `recall`의 실사용 형태다.

**22. 검색 실패에서 재발견으로**
못 찾았을 때 유사어를 제안하고 관련 문서를 제시하며, 그래도 없으면 캡처를 유도한다. 검색 실패가 막다른 길이 되지 않게 한다. 실패한 질의는 기록해 두어 나중에 무엇이 없는지 파악하는 근거로 쓴다.

**23. easy 모드 에이전트 연동**
CLI 에이전트가 스킬 문서를 읽고 위키를 다룬다. `skills install` 한 번으로 붙는다. 여정 8이 MCP만 다루던 시절에는 이 동선이 hard 모드 전용으로 남아 있었다.

## D. 재발견

제품 정체성이 가장 뚜렷하게 드러나는 묶음이다. 사람이 손으로는 못 하는 일이다.

**9. 오래 안 본 문서 역제안**
"30일째 안 봤습니다. 아직 유효한가요?" 유효, 폐기, 보강 세 갈래로 답한다. 제시 이력을 상태 파일로 관리하므로 같은 문서가 매번 나오지 않는다.

**10. 연관 제안과 묶기**
유사하지만 링크가 없는 문서 쌍을 알리고 묶을지 묻는다. 수락하면 양방향 링크를 넣거나 상위 개념 노드 생성을 제안한다. 기각한 쌍은 영구 기록해 다시 묻지 않는다.

**11. 정기 다이제스트**
기간 요약. 신규, 승급, 노후, 고아 문서를 집계한다. **고아의 정의는 링크 0개다.**

## E. 운영

**12. 드리프트 점검과 대량 마이그레이션**
스키마를 바꾸면 기존 문서 수백 개가 따라와야 한다. `migrate --dry-run`이 기본이다. upstream에서 실제로 반복해 겪은 문제이고 그때마다 일회성 스크립트를 만들었다. 그 흔적이 이 여정의 근거다.

**13. 동기화와 충돌**
2대 이상의 PC를 git으로 맞춘다. 프론트매터 병합을 지원해야 한다. 같은 문서의 서로 다른 속성이 양쪽에서 바뀌는 상황이 흔하다.

**14. 외부 반출**
보고서, 블로그, 발표자료로 내보낸다. 익명화와 민감도 필터가 걸린다. 사내 교육 맥락에서 필수다.

**15. 팀 공유**
개인 위키 일부를 팀과 공유한다. `serve` 웹 UI가 여기 붙는다.
