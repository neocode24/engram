# 인증서 만료로 내부 호출이 끊긴 일

## 경과

2026년 5월 13일 새벽 4시 12분에 내부 게이트웨이와 회원 서비스 사이의
인증서가 만료되었다. 외부에서 보이는 서비스는 멀쩡했고 로그인 이후
동작만 실패하는 상태였다. 새벽에는 내부 트래픽이 없어 실패가 조용히
쌓였고, 우리 모니터링에는 아무것도 잡히지 않았다.

| 시각 | 내용 |
|---|---|
| 04:12 | 인증서 만료. 뒤늦게 확인한 시각 |
| 09:38 | 클라이언트 팀 문의 수신으로 발견 |
| 09:44 | 원인이 인증서 만료임을 확인 |
| 09:51 | 새 인증서 발급 및 교체, 재시작 |
| 09:53 | 정상화 확인 |

## 조치는 5분, 발견은 5시간 반

발급과 교체에는 5분이면 충분했다. 사건의 크기는 발견이 결정했고 두
가지가 겹쳐 늦었다. 만료 시각이 새벽이었다는 점도 발견 지연에 겹쳤다.
내부 트래픽이 없는 시간대라 실패가 드러날 창구가 아침까지 없었다.

모니터링에 인증서 만료를 보는 지표가 없었다. 실패율 지표는 있었지만
게이트웨이 뒤쪽 통계를 집계하는 자리라 이 실패를 잡지 못했다. 만료
안내 메일은 한 달 전부터 발급처에서 오고 있었으나 수신 주소가 옛
담당자의 개인 메일이었다. 그 담당자는 3월에 다른 팀으로 옮겼고 주소만
남아 있었다. 나흘 전 온콜 인수인계 대화에서 만료 메일을 봤다는 얘기가
오간 기록이 있으나 그 메일이 발급처가 보낸 것인지는 확인되지 않았고,
어차피 아무도 열어 보지 않은 것으로 본다.

## 재발 방지

| 항목 | 상태 |
|---|---|
| 만료 14일 전 경보 추가 | 설정 완료 |
| 수신 주소를 공용 그룹으로 교체, 인증서 목록에 만료일 병기 | 담당 미정 |
| 내부 인증서 목록 문서화 | 목록은 뽑았고 문서화 미완 |

목록을 뽑게 된 계기는 사건 경과에 있다. 내부에 어디에 어떤 인증서가
있는지 아는 사람이 없었다는 것이 재발 방지 논의에서 확인됐다.

경보를 넣어도 보는 사람이 없으면 소용이 없다는 것이 남는 의문이다.
수신 주소 문제와 같은 구조라서, 알림이 도착할 자리가 있는지가 경보
자체만큼 중요하다. 인수인계가 매번 구두로만 이루어지는 구조의 문제는
[[oncall-handoff]] 에서 따로 다룬다. 사고 기록 색인은 [[index]] 를
본다.
